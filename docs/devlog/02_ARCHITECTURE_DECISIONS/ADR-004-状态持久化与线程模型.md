# ADR-004：状态持久化与线程模型

- 状态：**已接受（2026-10-26，用户确认「ADR 确认，开始第三阶段」）**
- 日期：2026-10-26
- 决策人：用户 + Trae AI
- 关联：ADR-002、ADR-003；`01_RESEARCH_LOG.md` 2.2/2.4
- 影响范围：`app/services/checkpointer.py`、`app/api.py`、`app/ui.py`、`app/config.py`、测试与部署说明

---

## 1. 背景

HITL 要求图在红色风险处暂停，并能在 API/Streamlit 下一次请求时恢复。状态必须：

- 跨请求、跨进程重启保留；
- 与 `thread_id` 绑定，恢复时能取到同一份状态；
- 单机、无外部数据库服务；
- 测试时能完全不落盘；
- 不把合同文本、规则结果、人工意见写进不可控的位置。

同时本项目禁止 Docker、禁止引入 Postgres/Redis 作为默认依赖，10 天内不搭数据库运维。

---

## 2. 可选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. `InMemorySaver` | 进程内存保存 checkpoint | 零配置、测试最快 | 进程重启即丢；Streamlit/FastAPI 多进程不共享；不能作为演示的 HITL 持久化 |
| B. `AsyncSqliteSaver` | 单文件 SQLite 保存 checkpoint | 无需服务；跨重启；单机演示足够；依赖已支持 | 单写者/并发有限；不能水平扩展；需要处理连接生命周期 |
| C. `AsyncPostgresSaver` | PostgreSQL 保存 checkpoint | 并发/多实例/生产级 | 需要数据库服务；违反“不引入重型依赖”的 MVP 约束；部署复杂 |
| D. Redis checkpointer | Redis 保存 | 快、可过期 | 需要 Redis 服务；持久化配置复杂；比赛环境不可控 |
| E. 自定义 JSON 状态 | 自己序列化 state 到文件，恢复时重建图 | 完全可控 | 重造 checkpoint；难以处理中断点、版本、并发与恢复语义；容易漏状态 |

---

## 3. 决策

**采用 B：`AsyncSqliteSaver` 作为运行/演示的持久化；测试使用 A：`InMemorySaver`。**

### 3.1 组件与职责

```text
app/services/checkpointer.py
  ├─ create_checkpointer() -> AsyncContextManager[BaseCheckpointSaver]
  │    ├─ CHECKPOINT_BACKEND=sqlite → AsyncSqliteSaver.from_conn_string(path)
  │    └─ CHECKPOINT_BACKEND=memory → InMemorySaver（仅测试/无持久化开发）
  └─ 启动时创建父目录、设置 PRAGMA、健康检查

app/services/review_store.py（计划）
  ├─ pending/{review_id}.json    # 待审索引：review_id/thread_id/requested_at/status
  ├─ reviews/{review_id}.json    # 最终报告（END 之后写）
  └─ audit/{review_id}.jsonl     # 可选：append-only 事件（审批、报告生成）
```

**已验证的导入路径（2026-10-26 下载 `langgraph-checkpoint-sqlite==3.1.2` wheel 检查）**：

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver  # 注意：不是顶层包
```

- `AsyncSqliteSaver` **不在** `langgraph.checkpoint.sqlite` 顶层导出，必须从 `.aio` 导入；
- `AsyncSqliteSaver.from_conn_string(path)` 是 `@asynccontextmanager`，必须 `async with` 使用；
- 该包传递依赖 `aiosqlite>=0.20`、`langgraph-checkpoint>=4.3,<5`、`sqlite-vec>=0.1.6`；`sqlite-vec` 有 Windows amd64 wheel（`py3-none-win_amd64`），Python 3.12 可用；
- `StateGraph.compile(checkpointer=...)` 在 `langgraph==1.2.17` 中签名已核对。

> checkpointer 是**图状态的事实来源**；`pending/*.json` 只是索引，不能替代 checkpoint。报告是图跑完后的产物，单独落盘。

### 3.2 线程模型

- `review_id = "rev_" + uuid4().hex[:12]`（12 hex，足够 demo，不追求全局防碰撞）；
- `thread_id = review_id`；
- 一个 review 对应一个 thread、一份 checkpoint；
- 配置：
  ```python
  config = {"configurable": {"thread_id": state.review_id}}
  ```
- 不使用 `user_id` / `session_id` 作为 thread_id，避免多用户/多合同状态串线；
- 重新上传同一文件 = 新 review_id = 新 thread；不复用旧状态。

### 3.3 SQLite 配置

| 配置 | 值 | 理由 |
|---|---|---|
| 路径 | `.data/checkpoints.sqlite`（可由 `CHECKPOINT_SQLITE_PATH` 覆盖） | 单文件、易备份、易清理；不进 git |
| 日志模式 | `PRAGMA journal_mode=WAL` | 读写并发更好；单机足够 |
| 忙等待 | `PRAGMA busy_timeout=5000` | 避免短事务锁冲突直接失败 |
| 外键 | `PRAGMA foreign_keys=ON` | 数据完整性 |
| 连接生命周期 | FastAPI `lifespan` 启动时打开，关闭时释放 | 避免每请求新建连接；`AsyncSqliteSaver.from_conn_string` 是异步上下文管理器 |
| 并发写 | 单进程 + 每 review `asyncio.Lock` | SQLite 单写者；演示环境单进程足够 |

- 目录不存在时自动创建；
- 数据库文件启动时做一次 `SELECT 1` 健康检查；
- 备份 = 复制 `.data/checkpoints.sqlite`（WAL 模式下需同时处理 `-wal/-shm`，或先 checkpoint）。

### 3.4 启动与编译规则

```python
async def build_graph(checkpointer):
    builder = StateGraph(ContractReviewState)
    # ... add_node / add_edge ...
    return builder.compile(checkpointer=checkpointer)
```

- **启用 HITL 时必须提供 checkpointer**；没有 checkpointer 时编译直接抛错，不允许“静默降级为伪 HITL”；
- 测试用 `InMemorySaver` 编译同一张图；
- API/CLI 用 SQLite；规则评测模式可以完全绕过图（直接调规则函数），不需要 checkpointer；
- `MemorySaver` 仅用于单元测试与本地临时演示，启动日志必须打印“状态不持久化”的警告。

### 3.5 运行流程与落盘时机

```text
POST /review
  1. 生成 review_id
  2. graph.ainvoke(initial_state, config)
  3a. 若返回 __interrupt__ / snapshot.next 含 human_review：
        - 写 pending/{id}.json（status=awaiting_human, requested_at）
        - 写 audit（review_paused，不含最终结论）
        - 返回 {review_id, status: awaiting_human, hitl_payload}
  3b. 若跑完：
        - 写 reviews/{id}.json（最终报告）
        - 写 audit（review_completed）
        - 返回 {review_id, status: completed/approved/... , report}

POST /review/{id}/resume
  1. 读取 checkpointer 的 snapshot
  2. 校验 status=awaiting_human 且 next 含 human_review
  3. 校验/构造 HitlDecision
  4. graph.ainvoke(Command(resume=decision), config)
  5. 写 reviews/{id}.json；更新/删除 pending；写 audit
  6. 返回报告

GET /review/{id}
  1. 读 pending 索引 + snapshot
  2. 若 awaiting_human 且超时 → 自动 resume(timeout)
  3. 返回状态/报告
```

**关键**：最终报告与“审批通过”审计只在 resume 之后写；pending 元数据是允许的（见 ADR-002 3.5）。

### 3.6 超时与并发

- 超时检查是**惰性**的：`GET /review/{id}`、`GET /reviews/pending`、Streamlit 轮询触发；
- 每次检查先取 `asyncio.Lock`（按 review_id），避免 GET 与用户 POST resume 同时恢复；
- 超时 resume 使用 `{"action":"timeout","reviewer":"system",...}`；
- 若用户恰好在超时瞬间提交 approve，以先获得锁的请求为准；另一个请求看到状态已变更，返回现有结果；
- MVP 不启动后台线程，不引入 Celery/APScheduler；如果演示需要“无人访问也自动超时”，再评估后台任务。

### 3.7 失效与恢复

| 情况 | 行为 |
|---|---|
| 进程重启，SQLite 仍在 | `aget_state(config)` 可恢复；pending 索引仍在；用户可继续 resume |
| SQLite 文件损坏 | 启动健康检查失败 → 明确报错；不自动删库；提示备份/迁移 |
| 文件被删除 | 进行中的 review 无法恢复；API 返回 404/410；不允许重建为“通过” |
| schema 升级（state 字段变化） | 旧 checkpoint 可能无法反序列化；MVP 在 `state.schema_version` 记录版本；不兼容时返回明确错误，不静默忽略 |
| 同一 review 重复 resume | 状态幂等检查；已决策则直接返回现有报告 |
| checkpointer 不可用 | 启动失败（HITL 必需）；开发模式可显式选 memory 并打印警告 |

### 3.8 数据与隐私

- `.data/` 加入 `.gitignore`；合同原文、抽取字段、规则结果、人工意见都在其中；
- 演示/比赛使用脱敏合同；不把真实客户合同提交到仓库；
- 报告与 checkpoint 默认本地保存 30 天，提供清理脚本（MVP 可选）；
- 不把合同文本发送给除 LLM 供应商以外的第三方；
- LLM 日志不打印完整合同，只打印 `review_id`、条款 ID、hash 前缀。

### 3.9 测试策略

| 测试 | checkpointer | 断言 |
|---|---|---|
| 图单元测试 | `InMemorySaver` | 节点顺序、条件边、中断/恢复 |
| HITL 测试 | `InMemorySaver` | 审批前无最终报告、approve 只写一次、timeout 不通过 |
| API 集成测试 | `InMemorySaver` 或临时 SQLite | 3 个端点、pending 列表、幂等 |
| 重启恢复测试（可选） | 临时 SQLite | 关闭后重新打开，`aget_state` 仍能 resume |
| 规则评测 | 不用图/checkpointer | 纯函数，不依赖 LLM |

## 4. 被否决方案及原因

| 方案 | 否决原因 |
|---|---|
| `InMemorySaver` 作为演示默认 | 进程重启/多进程即丢；HITL 演示无法可靠恢复 |
| PostgreSQL / Redis | 引入服务依赖与运维；10 天 MVP 不需要；比赛环境不可控 |
| 自定义 JSON 状态 | 重造 checkpoint 语义；中断点、版本、并发、恢复都容易出错 |
| 用 `user_id` 做 thread_id | 多合同/多 review 会串状态；无法并发审查同一用户的多份合同 |
| 每次请求新建 SQLite 连接 | 生命周期混乱、锁竞争、性能差；应在 lifespan 管理 |
| 自动删库/重建损坏文件 | 丢失待审任务与审计；应显式报错并保留现场 |
| 后台常驻超时线程（首版） | 增加线程/生命周期复杂度；MVP 用惰性检查足够 |

## 5. 后果

### 正面

- 单文件持久化，零外部服务；重启后 HITL 仍可恢复；
- 测试用内存、运行用 SQLite，图代码不变；
- review_id/thread_id 一一对应，状态不会串；
- 报告、pending、checkpoint 分离，职责清楚。

### 代价与风险

- SQLite 单写者，不能水平扩展；比赛单机演示足够；
- 文件包含合同原文，需注意脱敏与 `.gitignore`；
- 惰性超时依赖有人访问 GET/UI；无人访问时任务会一直 pending；
- state schema 变更可能使旧 checkpoint 不兼容；必须维护 `schema_version` 与迁移说明；
- `AsyncSqliteSaver` 的连接生命周期需要正确关闭，否则 Windows 上可能文件锁；
- 同一 review 并发 resume 必须加锁，否则可能重复应用决策。

### 对后续模块的影响

- API 需要 `lifespan` 管理 checkpointer；
- Streamlit 需要轮询 `GET /review/{id}` 或直接调用服务层；
- 报告存储与 checkpoint 分离，清理策略要同时覆盖两者；
- `.gitignore` 必须包含 `.data/`、`*.sqlite`、`*.sqlite-wal`、`*.sqlite-shm`。
