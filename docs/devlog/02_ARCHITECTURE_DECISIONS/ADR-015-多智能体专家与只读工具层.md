# ADR-015：多智能体专家并行 + 只读工具层（本地工具 / MCP）

- 状态：**已接受（已实现）**
- 日期：2026-10-28
- 决策人：用户 + Trae AI

## 背景

用户反馈“离 agent 越走越远”：当前系统是**确定性 workflow**（`ingest → precheck → segment → extract → validate → rules → [HITL] → explain → report`），
只有两个 LLM 站（抽取、解释），没有多 Agent 协同，也没有 MCP / 外部 API 调用。

但这不是遗漏，是 ADR-001 / ADR-003 / ADR-006 的有意取舍：规则唯一判级、真 HITL、单机可跑、异常可降级、证据可追溯。
ADR-007（2026-10-27）已经**放开**“RAG + 多智能体 + 受限 Supervisor”，但 `AGENTS_ENABLED` 一直没实现，
缺的是“角色范围、是否接受额外 LLM 成本、接哪家外部 API”这几个决定（原 ISSUE-016）。

本轮用户明确“现在时间还有很多”，要求把 Agent 能力真正做出来，于是做出下面这个**边界内**的版本。

## 选项

**A. 自由对话式多智能体（Supervisor + ReAct + 任意转交）**
- 优点：最像“Agent”，演示效果强。
- 缺点：路径不可预测、成本不可控、无法写确定性回归测试；与 ADR-003（等级只来自规则）冲突风险最高。

**B. 确定性继承 + 并行专家节点 + 白名单路由**
- 优点：拓扑固定、可逐节点测试；专家只产出“候选意见”，等级仍由规则给。
- 缺点：编排不像“自主 Agent”，专家之间不能互相追问。

**C. 只做工具调用（function calling / MCP），不碰多智能体**
- 优点：改动最小。
- 缺点：仍是单 Agent，用户期待的“协同”没有体现。

**D. 接真实外部 API（制裁名单、汇率、HS 编码、企业征信）**
- 优点：最有实用价值。
- 缺点：全部要密钥与授权，且与 ADR-006“单机、无额外基础设施、可离线复现”冲突。

## 决策

选 **B + C**，D 只留接口不接真实服务。

### 1. 专家节点（并行，只提意见）

```text
validate_extraction ─┬→ expert_payment ─┐
                     ├→ expert_delivery ─┼→ collect_expert_findings → evaluate_rules
                     └→ expert_dispute ─┘
```

- 三个专家 **并行**（LangGraph 在条件边返回列表时自动 fan-out）；
- 路由是**确定性**的（`select_experts`）：按 `clause_type` 与关键词选，一个都没命中就跑全部（召回优先）；
  这就是 ADR-007 里“Supervisor 只做路由”的实现，但用 Python 写，零成本、可单测；
- 输出契约 `ExpertOpinion` / `ExpertDraft` **没有 `risk_level`**，`extra="forbid"`；专家给
  “主题 + 细节 + 修改方向 + 原文引文”；
- 引文必须能在该条款原文里定位（`locate_quote`），定位不到就**丢弃该条**并记 `expert:<id>:quote_not_found`；
- 每个专家最多 1 次 LLM 调用；失败 / 无 Key / 无条款 → 只写 `expert_notes`，不影响主流程；
- 并行分支**只写带 reducer 的字段**（`expert_findings` / `expert_notes` / `expert_route` 用 `operator.add`），
  `degraded_steps` / `warnings` / `expert_status` 由唯一的汇合节点 `collect_expert_findings` 写，
  避免 LangGraph 并发写同一 key 报 `INVALID_CONCURRENT_GRAPH_UPDATE`。

### 2. 工具层（只读，本地 + MCP）

`evaluate_rules` 之后、`explain_risks` 之前插入一个 `research_tools` 节点：

- **本地工具 4 个**（零网络）：`contract_outline`（条款目录）、`find_clause`（关键词定位）、
  `read_field`（回读已抽取字段 + 原文位置）、`search_knowledge`（复用 BM25 知识库）；
- **MCP**：实现 stdio / JSON-RPC 2.0 子集（`initialize` → `tools/list` → `tools/call`），
  不引入 `mcp` SDK（零新依赖）；服务器只来自 `.env` 的 `MCP_SERVERS`（JSON 数组），
  用 `shell=False` 启动、命令走白名单式校验、单行响应 ≤ 1 MB、超时即杀进程；
- **规划**：先让 LLM 输出 `ToolPlan`（≤3 次调用）；**没有 LLM 时退化为确定性计划**
  （用第一条 red/yellow 的规则标题去 `find_clause` / `search_knowledge`），保证离线也能演示；
- **白名单执行**：名字不在注册表的调用只记一条 `ok=False` 的轨迹，绝不执行；
- 每次调用都产出 `ToolCallRecord`（参数截断 200 字、摘要 400 字、耗时、成败、引用），
  进 `state.tool_calls`、报告 `tool_calls` 与逐条审查页的 `agent_trace`。

### 3. 解释侧只“读”，不“判”

`explain_risks` 新增两段数据区 `<untrusted_experts>` 与 `<untrusted_tools>`：

- 专家意见可被借用措辞与修改方向，**不得**据其增删风险或改等级；
- 工具结果里的 `source_id#section` 允许被引用（是工具读到的原文，不是模型编的），
  但仍受引用白名单约束：`allowed_citations = 本条 RAG 命中 ∪ 工具返回的 citation`；
- 两段都做 `</untrusted_*>` 转义，防止数据伪造结束标签。

### 4. 默认关闭、可独立回滚

| 开关 | 默认 | 关闭时的行为 |
|---|---|---|
| `AGENTS_ENABLED` | `false` | 条件边直接进 `evaluate_rules`，拓扑等价于原主干 |
| `TOOLS_ENABLED` | `false` | `research_tools` 是零副作用空节点 |
| `MCP_SERVERS` | 空 | 只注册 4 个本地工具 |
| `MAX_TOOL_CALLS` | 3 | —— |

## 后果

**正面**
- 有了真正的“并行专家 + 工具调用”能力，且**不破坏**“规则唯一判级”；
- 全部可离线测试：`tests/test_agents.py`（12 项）、`tests/test_tools.py`（23 项，含伪 MCP 服务器）；
- 失败一律降级为 `degraded_steps` + `warnings`，审查结论不受影响（有对照测试：开/关专家与工具，`rule_id` 与 `overall_level` 完全一致）。

**代价**
- 开启后每次审查多 3 次 LLM 调用（专家）+ 1 次（工具规划）+ 至多 3 次工具执行；
- MCP 会多一个子进程；`shell=False` + 只读工具，但仍属于“外部进程信任边界”（记为 ISSUE-032）；
- 前端多两块 UI（专家参考意见、Agent 轨迹折叠面板），用中性色明确“不代表等级”。

**后续需要补**
- 专家资料（30–50 组“问题条款→改写”对照、让步顺序、品类模板）仍需用户提供，否则专家只靠模型常识；
- 真实外部 API（制裁名单 / 汇率 / HS 编码）要用户给密钥与授权范围才能接（D 项）；
- 成本：建议在 UI 上显示“本次额外调用 N 次”。
