# ADR-012：上传文档类型闸门（先判断是不是合同，再审查）

- 状态：**已接受（已实现）**
- 日期：2026-10-27
- 决策人：用户 + Trae AI

## 背景

用户上传了一篇法学论文（PDF）测试，系统却按“合同”跑完了条款切分、要素抽取与规则判级，还生成了风险清单。问题不在解析，而在**缺少“对象是否正确”的准入判断**：

- 规则引擎面对的是“任意文本”，论文里的“支付”“仲裁”“责任”同样能命中关键词；
- 一旦进入 `human_review`，会要求人工确认红色风险，等于把错误前提放大成正式流程；
- 报告若显示“总体等级”，会被误读为“这篇论文有合同风险”。

约束不变：等级仍只由 Python 规则决定、LLM 只做抽取与解释、HITL 必须真暂停、异常必须降级；不得引入 LLM 做准入（不可复现、离线不可用、成本不可控）。

## 选项

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 前端只允许选择合同类文件名 / 让用户自己勾选“这是合同” | 否 | 文件名不可信；用户勾选等于没有校验 |
| B. 用 LLM 判断文档类型 | 否 | 需要 Key、慢、不可复现，且与“规则唯一判级”边界混淆 |
| C. 确定性规则闸门 `precheck_document`（采用） | 是 | 纯 Python、可离线、可解释、可测试；误判有明确理由可人工复核 |
| D. 只靠条款数量/结构 | 否 | 论文也有“第一章/第一条”式结构，单独用会误判法规 |

## 决策

在 `ingest_document` 之后、`segment_clauses` 之前新增 **`precheck_document`** 节点（`app/nodes/precheck.py`），调用 `app/services/document_type.py::classify_document`，写 `state.document_check`：

1. **身份信号**：合同抬头（销售/买卖/采购/供货…合同，Sales Contract 等）、合同编号（`合同编号：C47`、`Contract No.`）、买卖双方（卖方/买方、甲方/乙方、Seller/Buyer…）。三者全无 → 判否。
2. **反向信号**：学术论文（摘要、关键词、参考文献、本文认为、this paper…）与法规条文（本法、民法典、总则、Civil Code…）。出现且**没有合同编号/签署语** → 判否。
3. **契约度评分**：抬头 3、编号 2、双方 2、编号条款（≥2 条“第 X 条”或 ≥3 条编号段落）2、交易要素 ≥3 项 1、签署语 1；总分 < 4 → 判否。
4. 正文去空白 < 120 字 → 判否（封面/空白页/扫描件无文本）。

判定为否时：

- 图经条件边直接跳到 `build_report`：**不切条款、不抽取、不判级、不触发 HITL**；
- 新增状态 `not_contract`（`ReviewStatus` 联合类型），报告 `status=not_contract`、`findings=[]`、`overall_level=unknown`；
- 报告摘要写明“未执行合同审查”及判定依据，`limitations` 增加一条明确说明；
- `ReviewSummary.document_check` 暴露 `is_contract/confidence/reasons/hints`，前端直接展示“判定依据 / 下一步”，不再展示风险结论；
- API `API_VERSION` 0.8.0 → **0.9.0**（新增字段与状态值）。上传仍返回 201（保留审计记录与可下载的“未执行”报告），由 `status` 区分。

同时，面向业务用户**移除侧栏“运行环境”块**（接口版本 / 规则集版本 / checkpoint / RAG 开关）：这些是实现细节，不是审查人员需要的信息；`/docs` 入口保留。

## 后果

**正面**

- 论文、法规、说明书等材料不会再被当成合同审查，也不会产生“总体等级”；
- 判定是纯规则、可复现、可解释，离线可用，不依赖 LLM；
- 报告与接口都保留判定依据，用户知道“为什么拒绝”和“下一步怎么办”；
- 90 份合同语料全部通过闸门（0 误杀），真实论文 PDF 置信度 0.98 判否，法规 PDF 判否。

**代价 / 风险**

- 闸门是**召回优先**：只要标题/编号/双方齐全且评分达标就放行，宁可放过也不误杀；极端“像合同的论文”仍可能进入审查，但会在报告中体现抽取与判级结果；
- 中文英文以外的语言（如日文、德文合同）没有专门词表，可能被误拒；扩展词表需要真实样本，不在本轮范围；
- `not_contract` 进入 `FINAL_STATUSES`：终态后再提交人工决定是幂等空操作，不会“复活”一个被拒绝的文件；
- 新增节点与状态让图多一个条件边，`ContractReviewState` 增加 `document_check`，历史 checkpoint 缺该字段时为 `None`（向后兼容，读取时按“未判定”处理）。

## 证据

- 规则：`app/services/document_type.py`（阈值与词表集中在文件顶部，含中文/英文）
- 节点与路由：`app/nodes/precheck.py`、`app/graph.py`（`ingest → precheck → segment | report`）
- 契约：`app/schemas.py`（`DocumentCheck`、`ReviewStatus += not_contract`、state 字段）、`app/api.py`（`ReviewSummary.document_check`、`API_VERSION 0.9.0`）
- 报告：`app/nodes/report.py`（`NOT_CONTRACT_LIMITATION`、摘要、状态映射）、`app/report_markdown.py`、`app/ui.py`
- 前端：`app/web/app.js`（`renderNotContract`、工作台六步流水线与提示、移除运行环境）、`app/web/index.html`
- 测试：`tests/test_document_type.py`（11 项：论文/法规/过短/90 份合同语料/两个样例/图集成）、`tests/test_api.py::test_non_contract_upload_is_not_reviewed`、`tests/test_web.py::test_runtime_internals_stay_out_of_the_ui`
- 实测：论文 PDF `全球比较下的我国人工智能立法_丁晓东.pdf` → `not_contract`、置信度 0.98、0 条 findings；C47 → `is_contract=true`、评分 11/11、11 条编号条款；全量 `pytest` **257 passed**、`ruff check .` 通过
