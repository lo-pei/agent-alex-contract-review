# ADR-001：图结构选型

- 状态：**已接受（2026-10-26，用户确认「ADR 确认，开始第三阶段」）**
- 日期：2026-10-26
- 决策人：用户 + Trae AI
- 关联：`01_RESEARCH_LOG.md` 第 4/6 节；ADR-002、ADR-003
- 影响范围：`app/graph.py`、`app/nodes/*`、状态 schema、测试与评测的整体形状

---

## 1. 背景

本项目 10 天 MVP，必须同时满足以下硬约束：

1. Python 函数规则引擎负责风险等级（`red / yellow / pass`），LLM 不参与判级；
2. LLM 只做条款要素抽取与风险解释；
3. HITL 用 LangGraph `interrupt()` + checkpointer + `Command(resume=...)`；
4. 覆盖：文档提取 → 条款切分 → 要素抽取 → 规则判定 → 条件路由 → 风险解释 → 报告；
5. 异常（LLM 超时/非 JSON、空合同、HITL 超时）必须有降级路径，不能崩溃；
6. 禁止 Supervisor、多智能体、RAG 知识库、训练模型、Docker、重型前端。

合同样本预计 3–20 页、5–40 个条款，单用户演示，不需要高并发。关键目标不是“像 Agent”，而是**可解释、可测试、可复现、能现场演示 HITL**。

---

## 2. 可选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. Supervisor 多 Agent | 一个调度 Agent 决定调用哪个子 Agent，子 Agent 可互相转交 | 看起来“智能”；扩展节点容易 | 流程不确定、可能循环；难评测；难解释为什么走某条路径；与禁止 Supervisor 冲突；10 天调试成本高 |
| B. 并行分支（LangGraph `Send` / 多边） | 条款抽取、规则检查、合规检查并行，汇合后合并 | 理论延迟低 | 状态合并、错误合并、进度展示复杂；HITL 前状态不确定；对 3–20 页合同收益有限 |
| C. 确定性顺序主干 + 条件边 + 单一 HITL 门 | 固定节点顺序，只有“是否有 red”和“HITL 决策”两个条件边 | 路径可预测、易测试、易解释；规则与 LLM 边界清晰；HITL 状态简单 | 需要自己定义稳定的状态与节点契约；条款多时串行延迟较高 |
| D. 单体 LLM Agent（ReAct） | 一个 Agent 用工具自由决定抽取、查规则、写报告 | 代码少；灵活 | 无法保证规则唯一判级；每次路径不同；不可回归；HITL 与报告难审计 |

---

## 3. 决策

**采用方案 C：确定性顺序主干 + 两个条件边 + 单一 HITL 门。**

### 3.1 图结构

```text
START
  │
  ▼
ingest_document（纯 Python）
  │  解析 PDF/DOCX/TXT → canonical text + pages + 全局字符偏移
  ▼
segment_clauses（纯 Python）
  │  条款切分 → Clause[]，保留 page/start/end
  ▼
extract_fields（LLM）
  │  结构化输出：字段值 + 原文引文；未提及 = null
  ▼
validate_extraction（纯 Python）
  │  引文核验、日期/金额/期限解析、一致性检查 → to_verify
  ▼
evaluate_rules（纯 Python）
  │  每条适用规则输出 red/yellow/pass + reason + evidence span
  ▼
route_by_risk（条件边函数，不是节点）
  │
  ├─ 存在 red（含系统级 red）──► human_review（interrupt + checkpointer）
  │                                  │
  │                                  ▼
  │                            route_after_hitl（条件边函数）
  │                              ├─ approve ──────────► explain_risks（LLM）
  │                              └─ reject/change/timeout ─► build_report
  │
  └─ 无 red ───────────────────────────────────────────► explain_risks（LLM）
                                                          │
                                                          ▼
                                                       build_report（纯 Python）
                                                          │
                                                          ▼
                                                         END
```

### 3.2 节点职责与纯度

| 节点 | 类型 | 输入 | 输出 | 是否有副作用 |
|---|---|---|---|---|
| `ingest_document` | 纯 Python | 文件路径/字节 | `pages[]`、`raw_text`、`sha256`、`warnings[]` | 只读文件；不写报告 |
| `segment_clauses` | 纯 Python | `raw_text`、`pages[]` | `clauses[]`（含 `page/start/end`） | 无 |
| `extract_fields` | LLM | `clauses[]` | `LLMExtraction[]`（字段值 + 引文） | 外部 LLM 调用；失败只记录，不写业务数据 |
| `validate_extraction` | 纯 Python | `LLMExtraction[]`、`clauses[]` | `ValidatedExtraction[]`、`to_verify[]` | 无 |
| `evaluate_rules` | 纯 Python | `clauses[]`、`ValidatedExtraction[]` | `RuleEvaluation[]`、`overall_level` | 无 |
| `human_review` | HITL | red findings、证据、抽取字段 | `HitlDecision`、状态 | `interrupt()` 暂停；resume 后只更新图状态，**不写最终报告/审计** |
| `explain_risks` | LLM | 非 pass findings、条款原文、规则理由 | `RiskExplanation[]`（不得含等级） | 外部 LLM 调用；校验失败用规则理由兜底 |
| `build_report` | 纯 Python | 全部状态 | `ReviewReport` | 无（API/CLI 在 END 后落盘） |

> 设计原则：**节点要么是纯函数，要么只有一个明确的外部调用**；不把“写数据库 + 调 LLM + 改状态”混在一个节点里。

### 3.3 条件边

```python
def route_by_risk(state) -> Literal["human_review", "explain_risks"]:
    if any(f.risk_level == "red" for f in state.rule_evaluations):
        return "human_review"
    return "explain_risks"


def route_after_hitl(state) -> Literal["explain_risks", "build_report"]:
    if state.hitl and state.hitl.action == "approve":
        return "explain_risks"
    return "build_report"
```

**为什么只有两个条件边**：
- 第一个只判断“是否有 red”，不判断“哪个 Agent 更合适”；
- 第二个只判断“人工是否批准”，不让人工决定流程走向；
- 其余全部固定顺序，测试可以断言 node 顺序。

### 3.4 为什么不用并行分支

- 规则引擎是毫秒级，真正慢的是 LLM 抽取/解释；把规则与 LLM 并行并不能减少总时长（仍要等 LLM）。
- 条款抽取如果按条款并发，会引入 LLM 限流、部分失败、结果顺序、状态合并问题；MVP 先串行，后续若 p95 超过目标，再用 `Send` 分批并发。
- 并行会让人工复核看到的“证据/字段/规则结果”存在版本不一致风险；顺序主干更容易保证同一版本快照。

### 3.5 为什么不用 Supervisor

- 本任务的流程是**业务确定**的，不需要模型决定“下一步做什么”；
- Supervisor 的自由路由会让评测无法复现，也让 HITL 的“审批对象”不稳定；
- 评审追问“为什么走这一步”时，顺序图可以逐节点解释；Supervisor 只能回答“模型决定”。

### 3.6 状态 schema 草案

> 这是节点契约的统一形状；具体字段的 Pydantic 定义在 `app/schemas.py` 实现。LangGraph 1.2.17 支持 Pydantic / dataclass state（已检查源码中的 `_coerce_state`），本项目用 Pydantic BaseModel，节点返回**部分字段 dict** 进行更新。

```python
class ToVerifyItem(BaseModel):
    field: str
    reason: str
    clause_id: str | None = None


class ContractReviewState(BaseModel):
    model_config = ConfigDict(extra="forbid")

    # 版本与标识
    schema_version: int = 1
    review_id: str
    source_filename: str
    source_sha256: str
    media_type: Literal["pdf", "docx", "text"]

    # ingest / segment
    pages: list[Page] = []
    raw_text: str = ""
    warnings: list[str] = []
    clauses: list[Clause] = []

    # LLM 抽取 + Python 校验
    extraction_status: Literal["ok", "degraded", "skipped"] = "skipped"
    extractions: list[ValidatedClauseExtraction] = []
    to_verify: list[ToVerifyItem] = []

    # 规则（唯一等级来源）
    rule_evaluations: list[RuleEvaluation] = []
    overall_level: Literal["red", "yellow", "pass", "unknown"] = "unknown"

    # HITL
    status: Literal[
        "running",
        "awaiting_human",
        "approved",
        "rejected",
        "changes_requested",
        "completed",
        "unreviewed_red_risk",
        "failed",
    ] = "running"
    hitl: HitlDecision | None = None

    # 解释与报告
    explanation_status: Literal["ok", "fallback", "skipped"] = "skipped"
    explanations: list[RiskExplanation] = []
    report: ReviewReport | None = None

    # 可观测性
    degraded_steps: list[str] = []
    errors: list[str] = []
    timings: dict[str, float] = {}
```

`ReviewReport` 的最低字段：

```python
class ReportFinding(BaseModel):
    rule_id: str
    risk_level: Literal["red", "yellow"]
    reason: str
    suggestion: str | None
    clause_ids: list[str]
    citations: list[str]  # 文件名:p页:start-end
    explanation_summary: str | None
    explanation_grounded: bool


class ReviewReport(BaseModel):
    review_id: str
    source_filename: str
    generated_at: datetime
    overall_level: Literal["red", "yellow", "pass", "unknown"]
    status: str
    summary: str
    findings: list[ReportFinding]
    extracted_fields: dict[str, Any]
    to_verify: list[ToVerifyItem]
    hitl: HitlDecision | None
    limitations: list[str]  # 固定包含“预审辅助，不构成法律意见”
    rule_engine_version: str
    prompt_version: str
    model_id: str | None
```

**关键约定**：

- `overall_level` **只由规则引擎写**；LLM 节点返回的 dict 不包含该字段；`unknown` 只允许出现在 `evaluate_rules` 之前，最终报告必须是 `red/yellow/pass`；
- 若规则集加载成功但没有任何规则触发，`overall_level="pass"`；规则集为空/加载失败则启动失败，不允许“零规则运行”；
- 顺序图不需要 reducer；如果未来引入并行分支，必须给 `rule_evaluations` / `explanations` 等列表加 `Annotated[list, operator.add]` 并新增 ADR；
- `raw_text` 与 `pages` 保留在 state 中，保证 HITL resume 时不需要重新读文件；200k 字符上限下 SQLite checkpoint 可承受；若后续体积成为问题，改为内容寻址存储并更新 ADR-004；
- `schema_version` 用于 checkpoint 不兼容时的显式报错（ADR-004）；
- 暂停时 checkpoint 的 `status` 可能仍是 `running`（`interrupt()` 不提交节点返回的更新）；API/UI 的 `awaiting_human` 由 `snapshot.next` + pending 索引派生，详见 ADR-002。

## 4. 被否决方案及原因

| 方案 | 否决原因 |
|---|---|
| Supervisor / 多 Agent | 违反硬约束；流程不确定、难评测；10 天内容易出现循环与状态污染 |
| 并行分支（首版） | 对 3–20 页合同收益低；错误合并与状态版本复杂；HITL 前状态不稳定 |
| 单体 ReAct Agent | 规则无法唯一判级；流程不可回归；报告不可审计 |
| 把 LLM 放在路由节点 | 路由必须由确定性条件决定；否则“为什么进人工”无法解释 |
| 为每个条款建一个子图 | 状态与 checkpoint 数量爆炸；MVP 不需要 |

## 5. 后果

### 正面

- 图路径固定，测试可断言节点顺序、条件边与降级路径；
- 规则结果、抽取字段、解释、人工决策在同一状态里，报告可追溯；
- HITL 只出现在一个位置，checkpoint/恢复逻辑集中；
- 符合“Workflow First / Agent Second”，答辩容易讲清楚。

### 代价与风险

- 串行 LLM 抽取在条款很多时较慢；后续可用 `Send` 按条款批量并发，但必须先保证状态合并与错误归并测试；
- 节点数量比“两个大节点”多，需要严格定义每个节点的输入/输出；
- 如果规则集过小，语义风险会漏；通过 `to_verify`、人工复核与规则扩充缓解，不靠 LLM 判级兜底；
- `route_after_hitl` 让“拒绝/超时”跳过解释；报告仍要展示规则理由与证据，避免信息缺失。

### 对后续模块的影响

- 状态 schema 必须包含 `overall_level`、`hitl`、`degraded_steps`、`warnings`；
- API 需要暴露“运行到中断”和“恢复”两种调用；
- 测试需要覆盖：无 red 快速通道、有 red 暂停、approve/reject/timeout 三条路径；
- 评测的规则模式可以完全绕过 LLM 与 HITL，单独验证规则。
