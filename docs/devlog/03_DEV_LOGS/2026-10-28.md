### 19.6 第 5 条：为什么会出现“快捷填入账号密码”

浏览器与密码管理器（Edge/Chrome、1Password、Bitwarden）会把“`<form>` 里有一个 `type=password` 输入”当成登录表单。API 配置弹窗正好是“一个表单 + 一个 password 输入”，于是点进去就弹“使用已保存的账号密码”。修复：

```html
<form id="llm-form" autocomplete="off">
  <input id="llm-key" name="llm_api_key" type="password"
         autocomplete="new-password" data-lpignore="true" data-form-type="other" />
```

- `autocomplete="new-password"` 是**关键**：浏览器据此认为这是“设置新密码”，不会列出已保存的凭据，也不会提示保存；
- `name` 用 `llm_api_key` 而不是 `password`，避免启发式识别；
- `data-lpignore="true"`（1Password）/ `data-form-type="other"`（部分 Chromium 扩展）抑制第三方密码管理器；
- 厂商、地址、模型输入也加 `autocomplete="off"`，防止邮箱/地址自动填充。
- 测试 `test_llm_form_does_not_trigger_password_autofill` 只检查 `#llm-form` 这一段，不误伤登录弹窗（登录必须保留密码自动填充）。

### 19.9 取舍与已知边界

- 头像存 data URL 而不是文件：单机 SQLite 场景省掉静态目录与清理逻辑；代价是每条 `GET /api/auth/me` 都会带这串（128px JPEG 约 10 KB，可接受），且服务端不做二次编码（只校验前缀与长度）。

- 没有“改密码 / 注销账号”：口令哈希没有版本化迁移路径，先不做（ISSUE-025）。

- **两个弹窗放进 `index.html` 静态节点**：`#skill-new-dialog`（含 `#skill-form`、`#skill-form-title`、`#skill-name/desc/instruction`、`#skill-error`、`#skill-login-note`、取消/提交）与 `#skill-import-dialog`（`#skill-drop` 拖拽区、`#skill-import-files` 选文件、`#skill-import-folder` 选目录、`#skill-import-input` / `#skill-import-dir` 两个隐藏 input、`#skill-import-log`）。放进静态 HTML 的好处：切页不丢输入、`showModal()` 的焦点管理由浏览器负责。
- **事件委托必须从 `#view` 挪到 `document`**：弹窗在 `#view` 外，原来 `dom.view.addEventListener` 收不到；`bindSkills()` 全部改 `document.addEventListener("click"/"submit"/"change"/"drop"/"keydown")`，按 id / `data-*` 过滤。

### 21.3 第 3 条：对话式流式输出 + 左右分屏逐条审查 + 一键更正 + 导出

**后端（新增 3 项，不重新判级）**

- `app/schemas.py`：`ClauseFinding`（规则号 / 标题 / 等级 / 理由 / 建议 / 解释摘录与引用 / 知识引用 / 原文引文）、`ClauseReview`（条款原文 + 命中规则 + `revised_text` / `revision_note`）、`ClauseReviewList`（条款列表 + `contract_findings` 合同级问题 + `revised_count` + `limitations`）。
- `app/services/clause_review.py`：`build_clause_reviews(state, awaiting_human)` 从图状态（`rule_evaluations` / `explanations` / `clauses`）聚合视图——**等级直接搬规则结果**（red/yellow/pass），条款级取“红 > 黄 > pass”；`skipped` 规则与非 red/yellow 结果不进入视图；一条规则命中多条条款时每条款都展示；没有条款归属的规则进 `contract_findings`（“全合同 · 建议新增条款”）。
- `REVISION_TEMPLATES`：14 个 `rule_id` → 示例条款文本（带 `___` 占位），同一条款多条规则按“红在前、黄在后”拼接、按 `rule_id` 去重；`REVISION_NOTE` 固定提示“示例条款，下划线处需按实际交易条件填写，签署前请专业人士复核”。
- `POST /api/reviews/{id}/export`：请求体 `{format: docx|pdf, clauses: [{clause_id, text}]}`（`extra="forbid"`，条款 ≤500），用 `app/services/clause_export.py` 生成“一、逐条审查意见 / 二、全合同问题 / 三、修订稿”三节 + 免责声明；未点“一键更正”的条款保留原文；`ExportError`（无条款 / 未知格式）→ 400；`Content-Disposition` 同时给 ASCII 兜底名与 RFC5987 `filename*=UTF-8''…`。
- `GET /api/reviews/{id}/clauses`：返回上面的 `ClauseReviewList`；`authorize()` 沿用“已入册记录只对归属账号可见”，越权/不存在统一 404。
- DOCX 复用 `python-docx`；PDF 用 `reportlab` + 内置 `UnicodeCIDFont("STSong-Light")`（不下载字体、不联网），`requirements.txt` 新增 `reportlab==4.4.4`。

**前端（`app/web/app.js`）**

- `renderResult(review)` 先判 `failed` / `not_contract`，再渲染 `.review-shell`：用户气泡（文件名 + 本次 Skill/审查重点）+ 助手气泡 `#ai-stream` + `#approval-slot`，最后才是 `#workbench`。
- **流式是“先取真结果、再逐句写屏”**：`chatNarrative(review, view)` 用真实数据拼句（条款数、红/黄/pass 条数、合同级问题、待确认提示、免责），`streamText()` 每 18ms 写 3 个字符 + `.stream-caret`；`prefs.motion`（减少动效）时整段直出；`stopStream()` 清定时器（切页 / 退出用）。后端 `POST /api/reviews` 是同步阻塞，**没有做真 SSE**——显示的是真实内容，只是按时序铺开。
- **流式结束才展开工作台**，并把 `#workbench.scrollIntoView({block:"start"})`（仅当它在视口下方）——否则对话把分屏挤出屏幕，用户以为“没有逐条审查”。
- **左右分屏**：`.workbench-grid` = `minmax(220px, 0.85fr) | minmax(0, 1.6fr)`；左侧 `#clause-list` 每行“序号 + 条款名 + 等级标 + 已更正✓”，有合同级问题时首行是“※ 全合同（N 处）”；右侧 `#clause-detail` 显示原文（`pre.clause-text`）、审查意见（`findingBlock`：等级标签 / 理由 / 修改建议 / 决策依据 / 原文引文 / 知识引用）、可编辑的 `#revised-input`（示例条款）与操作行。审查意见卡片也按“红在前、黄在后”排（`_by_severity`，只调顺序，等级仍来自规则）。
- **一键更正 / 撤销 / 全部更正**：`state.corrections[clause_id] = 最终文本`，只改前端状态（不写后端），列表行出现“已更正 ✓”、`#clause-meta` 显示“已更正 N 条”，导出时把这些文本 POST 给 `/export`；撤销从对象里删除键。合同级问题没有原文可替换，只展示“建议新增条款”文本，不提供更正按钮。
- **导出 DOCX / PDF**：`exportRevised(fmt)` 用 `fetch` 拿 `blob`，文件名从 `Content-Disposition` 的 `filename*=UTF-8''` 解出（`filenameFromDisposition`），`URL.createObjectURL` 触发 `<a download>`，4s 后 `revokeObjectURL`；失败写到 `#export-error`。
- `bindWorkbenchEvents()` 在启动段一次性挂到 `dom.view`：`data-clause` / `data-apply` / `data-revert` / `data-apply-all` / `data-export`；`renderApproval(review)` 改成**只返回 HTML**（保留 `approval.findings` / `findings_total` / “待您确认”），由 `#approval-slot` 挂载后再 `bindConfirm()`。

### 21.4 第 4 条：退出前的任务中断确认

- `hasActiveTask()` = `state.busy || state.taskActive || state.reviewStatus ∈ {awaiting_human, running}`；覆盖“上传/读取中、待人工确认、正在跑图”。
- 点“退出登录”时若有任务 → `openDialog("logout-confirm")`（`#logout-confirm`：标题“审查任务仍在进行”、说明“退出会中断这次任务，未确认的红色风险不会再生成报告…”、按钮“继续审查 / 仍然退出”）；没有任务才直接 `doLogout()`。
- 取消只是 `closeDialog("logout-confirm")`，不退出；确认走 `doLogout()`：先 `stopStream()`（避免定时器继续往已卸载的视图写），再清 `taskActive / clauseView / corrections / reviewStatus`，最后 `POST /api/auth/logout` 并回到上传页。
- 说明边界：这是**前端拦截**，后端没有“中断并清理任务”的接口；退出后 `awaiting_human` 的记录仍在，重新登录可从审查历史继续（不静默丢弃）。记 ISSUE-028。

### 21.5 踩到的坑

- **弹窗在 `#view` 外，事件委托失效**：按钮点了没反应。凡静态弹窗里的交互，`addEventListener` 必须落在 `document`（并且只绑一次）。
- **`.dialog` 宽度优先级**：`.skill-dialog` / `.confirm-dialog` 必须写 `.dialog.skill-dialog` 才压得过 `.dialog{width:460px}`（与界面轮 10 的 `.account-dialog` 同一个坑）。
- **`scrollIntoView` 会把整页顶跑**：条款列表切换用 `scrollIntoView` 会让页面跳；改成直接算 `list.scrollTop` 平移列表自身。
- **合同级问题不能标“红”**：最初所有 `contract_findings` 都画成红标；改成取组内最严重等级（有红则红、否则黄），否则“1 处黄色”也显示成红。
- **`font-size` 一律走 `--ui-text-scale`**：新增样式里每个字号都写 `calc(Npx * var(--ui-text-scale, 1))`，否则“界面字号 大”对新增区域不生效。
- **导出没有真“落盘”**：`export_clause_review` 在内存里生成字节直接回传，不写临时文件；`filename*=UTF-8''` 必须 `quote(safe="")`，否则中文名会被截断。

### 21.7 取舍与边界

- **不做真 SSE**：后端 `POST /api/reviews` 同步跑图（遇 HITL 暂停），要真流式得改成“提交任务 + 轮询/SSE 事件流”，属于后端架构改动；当前用“真实内容 + 前端节奏”满足“对话式流式”的观感，并在文档写清（记 ISSUE-027）。
- **更正只在前端**：不新增“保存修订”接口，避免把用户未签署的改稿当正式版本存库；关闭页面即丢，导出才是交付物。
- **修订文本是示例条款**：14 个模板覆盖当前 13 条规则的主要主题，未覆盖的 `rule_id` 不生成修订文本（只给建议），避免凭空编条款；模板带 `___` 占位与免责声明。
- **合同级问题不提“一键更正”**：没有原文可替换，只给“建议新增条款”文本；用户可在导出稿的“二、全合同问题”里看到。
- **退出确认是前端拦截**：不新增后端“取消任务”接口（需要处理 checkpoint、pending、上传文件清理与并发锁），记 ISSUE-028。

### 22.2 第 1 条：主题色下线，改“白天 / 黑夜 / 跟随系统”

### 22.8 第 8 条：条款切分精度

真实上传的 `国际贸易销售合同范本.docx` 被判成 7 条（“特别提示”里的 `1./2./3.` 也被当条款），逐行 dump 后定位 4 个根因，`app/nodes/segment.py` 逐个修：

- **“编号 + 主题词 + 冒号 + 正文”同一行**：新增 `_NUMBERED_HEADING`（≤600 字）与 `_LABEL_HEADING`（≤800 字），`is_heading()` 先判这两种、再判短标题模式；`MAX_NUMBERED_LINE_CHARS=600`、`MAX_LABEL_LINE_CHARS=800`。
- **字段行被当标题**（`装运港：  Port of Shipment:` 里“装运”命中 delivery 关键词）：新增 `_FIELD_LABELS` 前缀黑名单（卖方/买方/地址/电话/装运港/目的港/Port of Shipment…），`_is_label_heading()` 先排除。
- **“特别提示”块里的 `1. 2. 3.`**：`_notice_spans()` 标记说明块范围（起 `特别提示|重要提示|注意事项…`，止 `销售合同书|SALES CONTRACT|CONTRACT|合同编号|第X条|ARTICLE N`），`heading_starts()` 过滤。
- **中英对照被拆成两条**：`_merge_translations()` 用主题交集把相邻同主题段并回一条，`_starts_numbered()` 防止两条各自带编号的条款被误并。
- **小段合并误伤**：`_merge_small()` 改为只有“非标题开头的小段”才并入上一条（`headed = bool(title) or is_heading(first_line)`）。
- **标题过长/带占位空格**：新增 `_short_title()`，目录只留“编号 + 主题词”（`5. 付款条件：   Payment:` → `5. 付款条件`），正文仍在 `text` 里。
- **前言编号**：`ClauseReview` 增 `is_preamble`，前言显示“前言”、导出也不写成“第 1 条”；其余仍按条款顺序编号。

### 22.9 第 9、10 条：左目录+原文、右意见，三块各自滚动

- `.workbench-grid` 两栏等高：`height: min(66vh, 720px)`（`min-height: 360px`），左 `minmax(260px, 1fr)`、右 `minmax(0, 1.25fr)`。
- 左栏 `.clause-pane` 是 `display:flex; overflow:hidden`：上半 `#clause-list` 目录（自己 `overflow-y:auto`，序号列用合同自带编号、名称列去掉重复的“5.”，行内显示“高风险 / 需关注 / 保留 / ✓”），下半 `#clause-origin` **固定显示当前条款原文**（`max-height:42%`，同样自己滚）。
- 右栏 `#clause-detail` 直接给意见：等级标签 / 理由 / 修改建议 / 决策依据 / 原文引文 / 知识引用 / 可编辑修订稿，底部 `.detail-actions` = **采用修改 / 保留原文 / 撤销更正**；`state.kept[clause_id]` 与 `state.corrections` 互斥，列表显示“保留”标签。
- 三块都写 `overscroll-behavior: contain`，滚动不会“传染”给外层；窄屏（≤900）改成上下排列（目录 360px、右栏 `max-height:360px`）。

### 22.10 踩到的坑

- **主题色“改不动”的真因**：原来只改 `--accent`，且 `data-theme` 分支与 `.theme-dot` 的选中样式互相覆盖；直接下线比继续修更符合用户诉求。
- **深色变量留在 `@media` 里就没法手动切**：必须搬进 `html[data-scheme="dark"]`，`system` 才能靠 JS 解析成具体 light/dark。
- **`装运港：` 命中 delivery 关键词**：主题词判定必须先跑字段黑名单，否则表头行永远被判成标题。
- **中英对照合并会误并相邻条款**：加 `_starts_numbered()` 守卫，只合并“不带编号”的同主题段。
- **左栏塞两块内容**：目录和原文共用一个滚动条会让目录跟着原文跳；改成 `.clause-pane` 只做 flex 容器，目录/原文各自 `overflow-y:auto`。
- **`scrollIntoView` 会带跑整页**：目录选中用 `list.scrollTop` 自己平移。
- **`.skill-tag-quiet` 没定义**：`skillRow()` 用了但样式表没有，补一条弱化底色的定义。

### 22.11 验证

- `pytest` **334 passed**（`tests/test_segment.py` 新增“标题同一行也算标题”“中英对照不拆两条”“目录短标题”；`tests/test_clause_review.py` 新增前言标注；`tests/test_accounts.py` 新增 4 项：工具目录只读且顺序固定 / `tools`+`assets` 保存与 PATCH 改回 / 附件后缀与长度与数量校验 / `compose_focus` 含工具与附件且声明不执行；`tests/test_web.py` 新增 3 项并改写“对话流 + 分屏”“账户主题色”等旧断言）。

### 22.12 取舍与边界

- **Skill 附件绝不执行**：只作为“写法参考”拼进 focus，且明写不得当指令；服务端只做文本存储与长度校验，不做 AST 检查、不沙箱运行（记 ISSUE-029）。
- **工具是“声明的能力”，不是可编排的插件**：`TOOL_CATALOG` 与图节点一一对应、只影响 focus 文案，不改变判级与流程顺序。
- **历史刷新是前端主动拉取**：没有推送/订阅，`limit=20` 与控制台一致；审批徽标仍由原来的汇总接口维护。
- **裁图只在前端**：裁剪结果压成 128×128 JPEG，服务端不重新编码、不扫图（ISSUE-025 已记）。
- **左栏原文是“当前选中条款”**，不是全文阅读器；要看全文仍走导出的修订稿。


## 23. 界面轮 13：30 MB 上传、图片 PDF OCR、外部 Skill 内置、完整原文与 zip 导入

> 用户 5 条需求：① 上传限制适当扩大；② 加 OCR 识别 PDF 图片；③ 把桌面 4 个 Skill 包纳入默认仓库；④ 测试文版为什么有两个付款条件、合同名与“已完成”要同一行、想直接看完整原文而不是机械拆分；⑤ Skill 包导入支持 zip。

### 23.1 上传上限 15 → 30 MB
- `app/config.py`：`MAX_UPLOAD_MB` 默认值改 30；`.env.example` 同步；`.env` 补 30 与 OCR 变量。
- `app/web/app.js`：`MAX_BYTES = 30 * 1024 * 1024`，错误文案“文件超过 30 MB”，首屏加 `.composer-hint`“PDF（文本型或扫描件）/ Word / TXT / Markdown · 单个文件 ≤ 30 MB”。
- API 与 Streamlit 都读 `settings.max_upload_mb`（`app/api.py` 的 `limit_bytes`、`app/ui.py` 的 `limit`），只改一处即可；测试钉住前端常量，避免文案与实现再次漂移。

### 23.2 图片 PDF 的本地 OCR
- 新增 `app/services/ocr.py`：`pypdfium2` 渲染页面（`OCR_RENDER_SCALE=2.2`）→ `rapidocr-onnxruntime` 的 PP-OCR 模型识别；模型随 pip 包离线，**不联网、不训练、不写临时图片**。
- `app/nodes/ingest.py` 的触发条件：整份 `total_chars < 50` → 全页 OCR；否则只对单页 `< 10` 字的页补 OCR（页码/页眉不算正文）。
- 上限 `OCR_MAX_PAGES=20`，超出把剩余页写进 warnings；单页渲染/识别失败只跳过该页；依赖缺失或整份仍无文本 → `status=failed`，错误文案“请上传可复制文本的 PDF、DOCX 或 TXT”。
- 识别成功写 warning：“第 X 页没有文本层，已用 OCR 识别；识别结果可能有错字或串行，重要条款请人工核对”。
- **判级边界不变**：OCR 只产出 `raw_text`，后续切分/抽取/规则完全复用；`ClauseReview` 的等级仍来自 `rule_evaluations`。

### 23.3 4 个外部 Skill 包默认入库
- 包源复制到 `app/resources/skills/`（去空格重命名目录，保留 `SKILL.md` / `references/`）：
  - `letter-of-credit-reviewer` → `builtin:lc-reviewer`（信用证审单顾问）
  - `面向中国中小外贸企业…（虾评平台）` → `builtin:xiaping-fast-review`（外贸合同快审·虾评）
  - `外贸合同快审·小律同学AI（华为云）` → `builtin:xiaolv-fast-review`
  - `ai-contract-risk-officer` → `builtin:risk-officer`（AI 合同风控官）
- `packaged_skills()` 在导入模块时读取：`instruction` 用提炼的“关注方向”（受 1000 字上限），原包 `SKILL.md` 放附件第一位（便于直接读全文），随后按 `payment-terms → incoterms → risk-matrix → compliance → report-template → arbitration` 顺序取 `references/*.md`；最多 5 个、单个 6000 字，超长标“（节选）”。
- 工具只声明项目**已实现**的 5 个能力；原包里的 `allowed-tools` / 脚本不映射、不执行（ADR-003 判级边界）。
- 内置 Skill 7 → **11**；未登录也能看到（`builtin_skills()`），登录后与自建并列。

### 23.4 为什么出现两个“付款条件”
- 复现：历史记录 `4b82dd…`（界面轮 12 之前的切分）里是 `['5. 付款条件： Payment:'] × 2`；原因是旧切分把标题行后面的英文段（`Payment:` 开头的字段块）也当成新标题，于是同一主题被切两刀，第二条还把后面 4 个条款吞进去（4342 字）。
- 修法两层：
  1. `app/nodes/segment.py` 新增 `_merge_duplicate_headings()`：切分后、合并小段前，**相邻且主题词完全一致**的两条合并（`_topic_key` 去掉编号、冒号后正文和空白），偏移改为连续，原文仍可回溯；
  2. `app/services/clause_review.py` 新增 `_merge_adjacent_duplicates()`：旧记录不重跑也能在展示层合并（文本拼接、意见按红→黄排序合并、等级仍由原 findings 推出），合并后重排 `index`；旧标题用 `_display_title()` 截成“编号 + 主题词”。
- 同时把标题行里的长正文截掉：`5. 付款条件：                      Payment:` → `5. 付款条件`。

### 23.5 合同名与“已完成”同一行
- 删除 `.review-head-main` / `.file-line`；`#review-chips` 这一行依次是：合同文件名、Skill、审查重点、状态（`statusChip`）。状态 pill 去掉 `margin-left`，靠 `gap` 与标签等距。
- 长审查重点仍 `max-width:46ch` 省略 + `title` 悬停全文。

### 23.6 完整原文（“不要机械拆分”）
- `ClauseReviewList` 加 `contract_text = state.raw_text`，接口一次返回，前端不再额外请求。
- 左栏顶部 `.pane-tabs`：**条款目录**（默认，目录 + 当前条款原文）/ **原文全文**；`applyPaneMode()` 只切左栏，右栏意见不受影响；全文按 `\n\n` 分段、段内 `\n` → `<br>`，保留原始换行与编号。
- 全文块 `.contract-fulltext` 自己 `overflow-y:auto` + `overscroll-behavior:contain`，高度吃满左栏；`hidden` 用属性选择器压过 `display`。
- 取舍：默认仍进“条款目录”，因为逐条审查需要跳转；要看完整格式时一键切“原文全文”。

### 23.7 zip 包导入
- `skill_catalog.parse_skill_package(raw)`：
  - 只接受 zip（`BadZipFile` → 400），≤8 MB，解压 ≤40 MB，条目 ≤200；
  - 找层级最浅的 `SKILL.md`（大小写不敏感），frontmatter（`yaml`）取 `name/description/tags`，正文作审查重点（>1000 字截断并提示，完整内容仍在附件）；
  - 附件只收 `.py/.md/.markdown/.txt`，跳过 `__MACOSX`、点文件、>200 KB；`references/` 优先，按与内置包相同的顺序，最多 5 个；
  - `allowed-tools` **不映射**，只写 warning；
  - **不解压落盘、不执行**：测试包内放 `raise SystemExit(...)` 的 `check.py`，导入成功且进程存活。
- `POST /api/skills/import`（需登录，201）返回 `{skill, warnings, files}`；前端 `app.js` 的导入弹窗接受 `.md/.markdown/.zip`，zip 走该接口、Markdown 仍走 `POST /api/skills`，日志逐条显示“N 个文件 / N 个附件 / warnings”。

### 23.8 踩到的坑
- **`Sequence` 应从 `collections.abc` 导入**：`typing.Sequence` 触发 ruff UP035。
- **`Settings` 是 frozen dataclass**：测试里不能 `monkeypatch.setattr(settings, "ocr_enabled", ...)`，改为 `replace(settings, ...)` 后替换 `ingest` 模块里的引用。
- **`_TITLE_NUMBER_RE` 没捕获组**：`match.start()` 恒为 0，编号被吞成空串，目录出现“装运时间”没有“4.”；改成 `(\d{1,3})` 后按 `f"{group(1)}."` 还原。
- **`ingest` 的失败分支丢了 warnings**：OCR 的“未执行/已尝试”提示原本写不进 `state.warnings`，给 `fail()` 加 `extra_warnings` 参数。
- **OCR 识别会吞英文空格**：真实图片 PDF 输出 `SALESCONTRACT`、`2.PAYMENT`；不改识别模型，靠 warning 提示“重要条款人工核对”，且标题正则兼容 `2.PAYMENT` 形式。

### 23.10 取舍与边界
- **OCR 是兜底，不是主力**：只处理无文本层/图片页，最多 20 页；中文识别与表格版式仍可能错行，报告保留“人工核对”提示（ISSUE-030）。

## 24. 界面轮 14：多智能体专家并行 + 只读工具层（本地工具 / MCP）

> ADR：[ADR-015-多智能体专家与只读工具层.md](../02_ARCHITECTURE_DECISIONS/ADR-015-多智能体专家与只读工具层.md)。两个开关 `AGENTS_ENABLED` / `TOOLS_ENABLED` **默认 false**，关闭时拓扑与结论和界面轮 13 完全一致。

### 24.1 起因与定性
- 用户原话：“我觉得存在一个问题，我们离 agent 好像越走越远了，为什么没有多 agent 协同工作，mcp 或 api 调用呢”；随后补一句“我们现在不是已经完成大部分工作，时间还有很多，绰绰有余啊”——授权直接做，不用再等确认。
- 先按代码说实话：系统当时是 **确定性 workflow**（`ingest → precheck → segment → extract → validate → rules → [HITL] → explain → report`）+ 2 个 LLM 站 + 1 个 HITL 门；`AGENTS_ENABLED` 只在 ADR-007 里被“允许”，代码里不存在；`TOOL_CATALOG` 只是 Skill 文案；`function_calling` 只有结构化输出的回退。用户直觉是对的。
- 落地选择：**不改成聊天式 Supervisor / 单体 ReAct**（会破坏判级与可追溯），而是“固定主干 + 可选专家层 + 可选只读工具层”，路由用 Python 白名单，等价于 ADR-007 允许的“Supervisor 只做路由”。

### 24.2 三个并行专家（`app/nodes/experts.py`）
- `ExpertSpec` 定义 `payment`（付款与资金）/ `delivery`（交付与物流）/ `dispute`（争议与合规）：`clause_types` + 中英 `keywords` + 一段 `instruction`；`EXPERT_ORDER` 是展示与归一顺序。
- `select_experts()`：先看 `clause_type` 是否落在专家集合里，再看标题/正文前 300 字是否命中关键词；**一条都没命中就跑全部三个**（召回优先，宁可多花 3 次调用也不漏专业视角）。
- `route_experts()`：开关关闭 / `status == failed` / 无条款 → 返回 `"evaluate_rules"`，专家节点根本不进执行；否则返回 `[f"expert_{id}", ...]`，LangGraph 按列表**并行 fan-out**。
- 单专家：`_clauses_for()` 优先本专业条款（最多 8 条、每条 900 字），不足 2 条用其余条款补齐；1 次 `call_structured(llm, ExpertOpinion, ...)`；`_ground_findings()` 校验 `clause_id`、用 `locate_quote` 定位引文并写 `Evidence` + `format_citation`；找不到条款时只在引文能唯一定位时救回。
- 失败语义：无 Key → `expert:<id>:not_configured`；异常 → `expert:<id>:failed`；引文定位不到 → 丢弃该条 + `expert:<id>:quote_not_found`。全部只写 `expert_notes`，主流程照走。

### 24.3 并行写安全（踩坑）
- 第一版让每个专家顺手写 `timings` / `degraded_steps`，跑图直接 `INVALID_CONCURRENT_GRAPH_UPDATE`：LangGraph 的并行分支只允许写**带 reducer** 的字段。
- 改法：`ContractReviewState` 里 `expert_findings` / `expert_notes` / `expert_route` 用 `Annotated[list[...], operator.add]`；`finish()` 只回这三类字段。
- 汇合节点 `collect_expert_findings` **单点**写 `expert_status`（`skipped` / `ok` / `degraded`）、把 `expert_notes` 并进 `degraded_steps`、追加一条人话 warning；`expert_route` 按 `EXPERT_ORDER` 归一（并行 append 顺序不稳定，前端不能依赖）。

### 24.4 只读工具层（`app/services/tools.py`）
- `ToolSpec`（名称 / 标题 / 说明 / 参数名）+ `ToolOutput`（摘要 / 引用）+ `Handler`；`ToolRegistry.register()` 拒绝重名，`call()` **永不抛异常**，统一转成 `ToolCallRecord`（`name` / `ok` / `arguments` / `summary` / `citations` / `elapsed_ms` / `error`）。
- 截断：参数 200 字、摘要 400 字；失败也留痕（`ok=False` + `error`）。
- 4 个本地工具：
  - `contract_outline`：条款目录（编号 + 标题 + 字数）；
  - `find_clause(keyword)`：关键词定位，返回 `clause_id` + 引文可回溯摘要；
  - `read_field(field)`：回读已抽取字段值（只读）；
  - `search_knowledge(query)`：走既有 RAG（`RAG_ENABLED` 关时不注册）。
- `build_tool_registry(state, mcp_servers=..., timeout_seconds=...)` 统一装配；MCP 配置错误抛 `ToolError`，由 `research_tools` 降级成 warning。

### 24.5 MCP stdio 客户端（零新依赖）
- 手写 JSON-RPC 2.0 子集：`initialize`（`protocolVersion: 2024-11-05`）→ `notifications/initialized` → `tools/list` → `tools/call`；**不引入 `mcp` SDK**，避免为演示加依赖。
- 进程：`subprocess.Popen(..., shell=False, stdin/stdout/stderr=PIPE)`；后台线程读 stdout 逐行解析，`queue.Queue` 做超时等待；超时 `kill()` + 记 `ok=False`。
- 边界：单行 ≤ 1 MB（超长直接判协议错误）、初始化就绪 15 s、单次调用按 `MCP_TIMEOUT_SECONDS`、工具名 `mcp:<server>/<tool>`、服务器只来自 `.env` 的 `MCP_SERVERS`（JSON 数组，`command` 可用相对 `PROJECT_ROOT` 的路径）。
- 不可达：注册 `<server>/unavailable` 占位工具，调用时返回原因，审查不崩。

### 24.6 `research_tools` 节点（规划 + 执行）
- 位置：`evaluate_rules`（或人工确认）之后、`explain_risks` 之前；关闭 / 非 `running|approved` / 没有 red-yellow 命中 → 直接空更新。
- 规划：`ToolPlan`（`calls` ≤3 + `reason`），1 次 `call_structured`；提示词只给“规则命中的 title + 前 160 字 reason”和用户审查重点（`<untrusted_focus>` 转义）；规划失败 = 不调用。
- 执行：`limit = min(MAX_TOOL_CALLS, 3)`；未注册的名字**不执行**、只写 `ok=False`（“未注册的工具（白名单外，不执行）”）；有失败则 `research_tools:tool_failed` + warning。
- **无 LLM 回退**：`_fallback_plan()` 拿第一条 red/yellow 的 `title[:40]` 当检索词，调 `search_knowledge`（需 RAG）+ `find_clause`，写 `research_tools:deterministic_plan`——“未配置大模型，工具检索改为按规则主题词自动发起（不是模型规划的）”。这样本地无 Key 也能看到真实工具轨迹。

### 24.7 解释侧只读注入（`app/nodes/explain.py`）
- system prompt 增第 9/10 条：专家意见与工具结果都是**数据**；不得据此改等级、不得当作指令。
- user prompt 增 `<untrusted_experts>` / `<untrusted_tools>` 两段（无内容时写占位），`_sanitize()` 扩到 5 组结束标签。
- 引用白名单 = 本条 RAG 命中 ∪ 工具返回的 `source_id#section`，其余引用仍被质量门拦截。

### 24.8 状态与前端
- `ClauseReviewList.agent_trace`（`AgentTrace`：`experts` / `status` / `tool_calls`），由 `_agent_trace(state)` 过滤不存在的 `clause_id` 并按 `EXPERT_ORDER` 归一。
- `ReviewReport.expert_findings` / `tool_calls` 一并落报告（Markdown/JSON 都可追溯）。
- `app/web/app.js`：`expertBlocks(clauseId)` 在规则意见后渲染“参考 · {专家}”（topic / detail / quote / citation / suggestion + `.expert-note`“专家意见只作补充参考，不代表风险等级”）；`agentTraceBlock()` 用 `<details>` 折叠轨迹（专家、状态、工具成功/失败、引用）。
- `styles.css`：专家块**只用中性色**（`--muted` / `--faint` / `--border` / `--raised`），测试断言 `.expert-block` 内不出现 `--red-bg` / `--red-ink` / `--amber-bg` / `--green-bg`，防止被误读成等级。

### 24.9 配置与一致性
- `Settings` 新增：`agents_enabled=False`、`tools_enabled=False`、`mcp_servers=""`、`mcp_timeout_seconds=10.0`、`max_tool_calls=3`；`.env.example` 全部带注释与 JSON 示例。
- `/health` 返回 `agents_enabled` / `tools_enabled`；`API_VERSION` 1.0.0 → **1.1.0**。
- 一致性测试：同一份合同开/关专家，`rule_id` 与 `overall_level` 完全一致；工具端到端也只增 `tool_calls`、不改 findings 的 level。

### 24.10 踩到的坑
- **`dataclasses.replace(settings, tools_enabled=True, mcp_servers="", **overrides)` 重复关键字**：`mcp_servers` 同时是显式参数和 kwargs → 改为先构造 `values` dict 再 `replace(settings, **values)`。
- **计划 4 条但上限 3**：测试断言 3 次失败 → 不是 bug，改测试；执行上限保持不变。
- **`research_tools` 没传 `mcp_servers`**：`build_tool_registry(state)` 只读 settings 的原值，测试 monkeypatch 不生效 → 显式传 `settings.mcp_servers` / `mcp_timeout_seconds`。
- **`AgentTrace.experts == state.expert_route`** 因并行 append 顺序不稳定 → 测试按 `EXPERT_ORDER` 归一比较。
- **`build_user_prompt` 没有转义 experts/tools** → 在函数内部统一 `_sanitize()`。
- **专家用正则取第一条 `clause_id`** 会给出“合同里看不到的引文” → 改为只挑**真的包含该引文**的条款（`_quote_clause`），另写 `_bad_quote_llm()` 专测定位失败。
- **ruff E501**：伪 MCP 服务器的 `initialize` 结果单行 102 字 → 拆多行 dict。

### 24.11 验证
- `pytest` **386 passed**：新增 `tests/test_agents.py` 12 项（默认关闭、路由、无命中全跑、失败直进规则、schema 拒绝 `risk_level`、意见 grounded、引文不存在被丢弃、专家异常降级、无 Key、`agent_trace` 透出）；`tests/test_tools.py` 23 项（审计记录、未知工具拒绝、异常转 `ok=False`、参数截断、`search_knowledge` 受 RAG 开关控制、`parse_mcp_servers` 6 类非法、伪 MCP 服务器、MCP 不可达降级、关闭为 noop、干净合同跳过、白名单不执行 `rm_rf`、无 LLM 确定性计划、坏 MCP 配置、端到端 `tool_calls` 不改等级、prompt 两段与转义）；`tests/test_web.py` 新增 1 项（专家块与轨迹分离、无语义色）。
- `ruff check app tests` 通过；`node --check app/web/app.js` 通过。

### 24.12 取舍与边界
- **专家不判级、不投票**：3 个专家只产出“值得注意的点 + 修改方向 + 引文”，不参与 `evaluate_rules`，也不改 HITL 的审批载荷；想要“专家投票定级”必须先改 ADR-003。
- **路由是确定性的**：`select_experts()` 不调 LLM 是为了可测、零成本；代价是“新专业方向”必须改代码（新增 `ExpertSpec`），不是自动涌现。
- **MCP 是信任边界**：只跑 `.env` 里配置的 stdio 命令、只读、超时杀进程；但子进程本身的能力不受我们控制，对外部署需再评（ISSUE-032）。
- **成本可见性**：开专家 = 每次审查多 3 次 LLM 调用，开工具 = 多 1 次规划 + ≤3 次执行；两者默认关闭，演示时按需打开。

### 24.13 收尾补漏：报告/导出也要能看到专家与工具
- **发现的缺口**：`report_markdown.py` 里完全没有 `expert` / `tool_calls` 字样，`clause_export.py` 也只写规则意见——也就是说专家意见和工具轨迹**只有前端结果页能看到**，用户下载的 Markdown / DOCX / PDF 里看不到，等于“证据可追溯”在交付物上断了。
- **报告（`app/report_markdown.py`）**：新增 `## 专家参考意见（不参与判级）`（专家名 · 主题、条款、说明、原文摘录、位置、未定位提示、建议）与 `## 工具调用记录`（表格：工具、结果、耗时、参数、摘要/错误、引用）；两条都显式写“只作补充参考，不改等级”；没有内容时也写明“本次未产生可用的专家意见 / 未调用工具”，不留空白。
- **导出（`app/services/clause_export.py`）**：DOCX / PDF 在“修订稿”之后加“四、专家参考意见（不参与判级）”“五、工具调用记录”，数据取自 `ClauseReviewList.agent_trace`（不是另算一遍），失败调用也写错误原因。
- **降级原因上屏**：`AgentTrace` 新增 `expert_notes`（去重），把 `expert:<id>:not_configured / :failed / :quote_not_found` 透到前端；`app.js` 用 `EXPERT_TITLES` / `EXPERT_NOTE_LABELS` / `EXPERT_STATUS_LABELS` 翻成“付款与资金：未配置模型”“部分降级”，并在轨迹摘要里补“参考意见 N 条 · 工具 M 次 / 合计 X ms”，成本一眼可见。
- **测试**：`tests/test_report_markdown.py` +2（有专家/工具时两节都在、失败也留痕、等级不变；无内容时给显式说明）、`tests/test_clause_review.py` +1（用 python-docx 反读导出的 DOCX 文本，确认两节存在）、`tests/test_agents.py` 补 `expert_notes` 去重断言、`tests/test_web.py` 补“降级原因翻成人话”断言。

## 25. 界面轮 15：检索评测落地（ISSUE-018，ADR-016）

### 25.1 动机
- 用户上一轮给的目标是“真实效果 + 可复现指标 + 可追溯报告”三件；报告与轨迹在 `84820f7` 补齐后，**只剩检索指标**。本轮用户原话：“好的，按建议从检索评测开始”。
- ISSUE-018 卡了两轮：`data/knowledge/100问题.md` 里写的是概念标签（`CISG-25` / `INC-CIF A5` / `JI-CC-1`），语料真实引用是 `source_id#section`（`CISG-ZH#s27` / `INCOTERMS-2020#s12` / `SPC-CONTRACT-2023#第一条`）。不解决这一层，任何“召回率”都是假的。

### 25.2 gold 的两层映射（`eval/rag_gold.py` + `data/eval/rag_label_map.yaml`）
- 第一层：能被规则解析的标签走通用条号正则——`CISG-N` → `CISG-ZH#s{映射}`、`CC-N` → `CN-CIVIL-CODE#第{中文}条`、`LAW-N` → `CN-LAW-APPLICATION#第{中文}条`、`JI-CC-N` → `SPC-CONTRACT-2023#第{中文}条`；`JI-CC`（无条号）落到 `SPC-CONTRACT-2023#前言`。
- 第二层：需要人判断的 27 个标签写进 `rag_label_map.yaml`（Incoterms 按主题标题 `^2\.3` / `^CFR / CIF` / `^FOB：` / `^3\.3 保险费用`，红线按 `^🟡 黄线｜…`），文件带 `version: 1` 校验与正则预编译，写坏直接报 `GoldConfigError`。
- **一个标签 → 多条可接受片段**：`CISG-25` 解析成 `{CISG-ZH#s27, CISG-EN#s26, CISG-KEY#s25}`，命中任一即算召回；`strict` 用 `COMMENTARY_SOURCES={"CISG-KEY"}` 剔除解读稿，`lenient` 保留。
- **`gaps` 显式登记**：语料没有的标签（如 CLOUT）写进 `gaps`，含该标签且**没有任何可定位片段**的题单列“语料未覆盖”，不动分母。结果：95 题可评测、5 题未覆盖（#42/#69/#86/#87/#88）。
- 生成物 `data/eval/gold_rag.json` 可 diff：每题 `expected` / `strict` / `unresolved`，文件头带 `generated_at`、`corpus.chunk_count`、`sources`。

### 25.3 两套口径与指标层
- `eval/rag_eval.py` 只算指标（标准库 only）：`_first_rank()` 取首个命中位次；`_summarize()` 出 `hits` / `recall_at` / `mrr` / `not_found` / `rank_histogram`；`score()` 汇总 `overall{lenient,strict}`、`by_group`、`misses_beyond_k`、`not_top1`、逐题明细。
- `eval/run_rag_eval.py` 造两套运行参数：**ranking**（`top_k=5`、`min_score=0`，看排序能力）与 **production**（真实 `RAG_TOP_K=3` / `RAG_MIN_SCORE=1.0`，看线上会不会返回空）。**禁止把两套混读**：ranking 的 R@5 不代表线上能返回 5 条。
- gold 过期守卫：先 `validate_gold()` 校验每题的 `citation` 仍在当前 `kb.citations()` 里，过期直接 `exit 3`；测试 `test_committed_gold_matches_current_corpus` 再重建一遍比对提交文件。

### 25.4 评测暴露缺陷 → 只改排序的加权（`app/services/rag.py`）
- 首轮实测：lenient R@1 **0.516**、strict R@1 **0.158**。逐题看 `not_top1`：问“CISG 第 39 条”时 `CISG-KEY` 解读稿排第一，问“民法典第 584 条”时条号根本没进打分——BM25 只认词面。
- 加法：`ARTICLE_HEADING_BOOST=2.5`（提问点名条号 + 片段标题就是该条）、`PRIMARY_SOURCE_BOOST=1.1`（同一条文里条文原文再压过解读稿）、`SAME_SOURCE_BOOST=1.15`（提问点名法律名 + 片段就来自该来源，`SOURCE_HINTS` 12 条）。
- 约束：**只乘分数、只改排序**——不打分新片段、不做硬过滤、不清空结果、不碰判级；`_article_numbers()` 抽不出条号时 `_query_boosts()` 全返回 1.0，与加权前逐字一致（有断言）。
- 条号抽取正则 `第\s*(N)\s*(?:[（(][^)）]*[)）])*\s*条`，支持 `第39(2)条`、`第49(1)(b)条`、`第2条第2款`；标题匹配认 `第584条` / `第五百八十四条` / `第25条｜` / `Article 25`。
- **中文数字单一实现**：新建 `app/services/chinese_numbers.py`（`to_chinese_number` / `from_chinese_number`，上限 9999，越界抛 `NumberFormatError`），检索加权与 gold 构造共用一份，避免“评测命中而线上不命中”。

### 25.5 踩到的坑
- `to_chinese_number` 初版手写分支产出 `一百零十`、`五百二` → 改逐位算法 + `pending_zero` + `一十`→`十`，并用测试钉住 `110/101/1050/12`。
- `test_committed_gold_matches_current_corpus` 先失败（Q81 缺 `CN-CIVIL-CODE#第五百零二条`），根因就是上面的转换 bug；修好后 `python -m eval.rag_gold --write` 重建。
- gold 断言里按 heading 猜成 `CISG-ZH#第二十五条`，实际是 `CISG-ZH#s27`（section 是顺序号）→ 先看生成的 JSON 再写断言。
- `cn_number(0)` 期望 `GoldConfigError`、实际抛 `NumberFormatError` → 函数迁到 `chinese_numbers.py` 后，测试改断言 `NumberFormatError`。
- 来源提示测试断言遍历了 `sources`（字符串集合）而不是 `hits` → `'str' object has no attribute 'source_id'`，改成 `any(source.startswith("CISG") ...)`。
- 第 72 题实际问“第 3 条”，测试查询写成“第72条” → 按题目原文改查询。
- `CISG第39(2)条` / `第49(1)(b)条` 抽不出条号 → 括号段从“可选一个”改成 `(?:[（(][^)）]*[)）])*`，第 7 题从 miss 变命中。
