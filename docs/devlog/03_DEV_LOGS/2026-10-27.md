## 1. 本轮输入

用户指令（原文）：“我新增了60份模拟合同，请你查收，在knowledge中，然后继续下一步”。

查收结果与用户描述有差异，先记录事实：

| 项 | 实测 |
|---|---|
| 新增文件 | `data/knowledge/模拟合同1.md … 模拟合同6.md`（6 个） |
| 合同份数 | **50 份（C01–C50）**，不是 60 份 |
| 缺失编号 | 未发现 C51–C60；逐个 `## Cxx` 标题核对无遗漏 |
| 每份附带 | 「条款—问题映射摘要」表格（条款 → Q 编号 → 期望召回 → 干扰项） |
| 结构 | `## Cxx · 场景` → `**SALES CONTRACT**` → `### 第X条 …` → `### 签署页` → 摘要 |
| 特点 | 大量占位符 `[C] 天`、`[X]`、`[A]`；专业度高（CISG 排除/未排除、CIF 保险、或裁或审等） |

**处理决定**：模拟合同是**评测输入**，不是法规知识，因此

1. 原始 `模拟合同N.md` 保持不动（用户原始文件，不裁剪、不改写）；
2. **不写入** `data/knowledge/manifest.yaml`（不影响 RAG 引用白名单）；
3. 用脚本拆成单份合同 `data/contracts/C01.md … C50.md`（生成物，可重建）；
4. 摘要解析为结构化 gold，放 `data/eval/gold_contracts.json`。

## 2. 做了什么

### 2.1 `eval/prepare_contracts.py`（新建）

- 正则定位 `## Cxx · 场景` 与 `> **条款—问题映射摘要（Cxx）**`，按合同边界切片；
- 单份合同正文保留 `**SALES CONTRACT**` 与 `### 第X条`，剥离场景标题与摘要（避免评测时把答案喂给系统）；
- 解析摘要表格为 `expectations[]`：`clause / questions / expected_recall / distractors`；
- 输出 `data/eval/gold_contracts.json`：`version / note / contract_count / contracts[]`，其中 `note` 明确“这是检索期望，不是规则判级 gold”；
- 运行结果：**50 份合同、105 条映射、全部解析成功**。

### 2.2 `eval/run_eval.py`（新建）

- 用 `ReviewService.in_memory()` 逐份跑完整规则链路（解析 → 切分 → 规则），**不调用 LLM、不需要 Key**；
- 只统计“未跳过且等级为 red/yellow”的规则，输出：
  `rule_engine_version / rule_count / contract_count / contracts_with_hits / contracts_without_hits / level_counts / hit_counts / contracts[]`；
- 结果写 `eval/results/rules-YYYYMMDD.json`，并在文件内写明“未命中不等于无风险”；
- 由于规则级 gold（`合同 × rule_id → red/yellow/pass`）尚未标注，**不计算 precision/recall**。

### 2.3 首轮基线暴露的两个真实问题

| 问题 | 证据 | 处理 |
|---|---|---|
| `R-TRD-001` 在 40/50 份合同上误报“未约定 Incoterms 版本” | 50 份合同全部写 `Incoterms® 2020`，原正则 `Incoterms\s*(19|20)\d{2}` 不匹配 `®` | 正则改为 `Incoterms\s*[®™]?\s*(?:19|20)\d{2}`，规则 version 1.0 → 1.1 |
| 规则覆盖严重不足 | 修正后 45/50 全 pass，仅 5 份命中 `R-PAY-002` | 扩充 6 条规则（见 2.4） |

> 顺带核实：`R-PAY-002` 的 5 次命中（C39–C43 一类）不是误报——那些合同确实没有付款条款（已逐份查看 C39 全文确认）。

### 2.4 规则集 7 → 13 条（`app/rules/definitions.yaml`，`version: 3`）

| rule_id | 主题 | 等级 | 正则/条件要点 | 命中 |
|---|---|---|---|---|
| R-DIS-003 | 仲裁与诉讼并列（“或裁或审”） | red | `仲裁[^。]{0,60}(?:或|或者)[^。]{0,40}(?:人民法院|法院|诉讼)` | C47 |
| R-DIS-004 | 仲裁裁决后仍可向法院起诉 | red | `仲裁裁决[^。]{0,30}后[^。]{0,60}(?:人民法院|法院|诉讼)` | C48 |
| R-INS-001 | CIF/CIP 约定投保但未写保额/比例 | yellow | CIF/CIP + 保险表述 + 无“保额 … %/合同价” | C04 |
| R-INC-001 | 贸易术语与运费承担矛盾 | yellow | `(?:FOB|EXW|FCA)[\s\S]{0,160}运费由卖方(?:预付|承担)` | C11 |
| R-INC-002 | FOB/EXW 用于整箱集装箱货物 | yellow | `(?:FOB|EXW)[\s\S]{0,120}(?:集装箱|FCL|拼箱|LCL|堆场)` | C23 |
| R-INP-002 | 检验/通知期限以小时计（极短） | yellow | `\d{1,2}\s*(?:小时|hours?)[^。]{0,30}(?:检验|通知|异议)` | C09 |

三个“踩过的坑”，已写进 ADR-010 与交接文档：

1. **`®` 必须容忍**：ICC 官方写法是 `Incoterms® 2020`；
2. **跨句要显式允许**：C11 的 FOB 与“运费由卖方预付”之间隔着句号，必须用 `[\s\S]{0,160}` 而不是 `[^。]`；
3. **不要重复 Incoterms 默认规则**：`R-INS-001` 只在“约定了投保但没写保额”时触发；CIF 完全没写保险条款（C09/C15/C40、干净样例）不触发，因为 Incoterms® 2020 已默认 110% + ICC(C)。

## 3. 第 2 轮：silver gold + 指标 + 留出验证

### 3.1 为什么必须先定口径，再谈数字

50 份合同的 6 条新规则是**在这批合同上设计的**。如果再拿这批合同的命中结果当 gold，P/R 必然是 1.0 —— 这是自证，不是评测。所以本轮先定三件事：gold 的来源、指标的分母、留出集的独立性。

### 3.2 `data/eval/gold_rules.json`（silver gold，21 个现象）

- 11 个映射到规则：6 条新规则各 1 个（C04/C09/C11/C23/C47/C48）+ `R-PAY-002` 5 个（C39–C43）；
- **10 个明确标 `rule_id: null`**，即规则缺口：
  - C39/C40/C41/C42/C43 缺「不可抗力」条款（5 个）；
  - C03/C13/C14 纯货物合同缺「检验/验收」条款（3 个，其中 C13/C14 只有“通知/知情”陈述）；
  - C41/C42 缺检验条款（2 个，与上条不重复计数）。
- 文件内固化标注口径（`annotation_protocol`）与 `provenance: silver，待人工复核`；`scored_rules` 只含 11 条文本规则，两条字段规则列在 `unscored_rules` 并注明“评测不调 LLM，运行时 skipped”。

### 3.3 `data/contracts_holdout/H01–H08` + `gold_holdout.json`（独立留出集）

刻意不沿用 50 份语料的模板：中英混排、同义改写、条款顺序不同。设计对照如下：

| 合同 | 设计意图 | 期望 |
|---|---|---|
| H01 | 英文 `either … arbitration, or … court`（或裁或审） | `R-DIS-003` 应触发 |
| H02 | 英文 CIF + “all risks”，无保额 | `R-INS-001` 应触发 |
| H03 | 中文“海运费及舱位订舱费用由卖方承担并预付” | `R-INC-001` 应触发 |
| H04 | 干净 CIF（ICC(C) + 110% + 全部规范条款） | **零触发**（误报对照） |
| H05 | 48 小时检验 / 12 小时通知 | `R-INP-002` 应触发 |
| H06 | 先裁后审 | `R-DIS-004` 应触发 |
| H07 | FOB + FCL + 堆场 | `R-INC-002` 应触发 |
| H08 | 无付款条款 | `R-PAY-002` 应触发 |

### 3.4 `eval/metrics.py`：三组指标

- `rule_level`：`合同 × 规则` 二分类，TP/FP/FN/TN + P/R/F1 + `level_agreement`（预测等级与 gold 是否一致）；
- `contract_level`：合同是否被正确标记，直接给出漏报/误报合同清单；
- `coverage`：gold 现象中被规则覆盖的比例，未覆盖部分即**规则缺口清单**；
- 零分母返回 `null`；gold 冲突/未知合同/未知规则/非法等级在加载期抛异常。

### 3.6 两个真实漏报（本轮故意不修）

| 合同 | 现象 | 为什么漏 | 结论 |
|---|---|---|---|
| H01 | 英文 “either submit … to arbitration, or bring an action before the competent court” | `R-DIS-003` 正则只写中文“仲裁…或…法院/诉讼” | 规则缺英文同义表达 |
| H03 | “**海运费**及舱位订舱**费用由卖方承担并预付**” | `R-INC-001` 要求“运费由卖方”紧邻；实际是“费用由卖方承担并预付” | 规则关键词语序耦合过紧 |

**故意不回改**：一旦按留出集调正则，H01/H03 就不再是留出样本，指标会立刻虚高。正确做法是：下轮修规则 + **另写一批新留出集**再验（ISSUE-021）。

值得注意的是 H02（英文 CIF + all risks）被命中，但命中的是 `R-INS-001` 的 `insurance` 关键字（第 5.2 条 “insurance policy”），属于**碰巧命中**。这说明英文支持不能靠运气，需要系统性补。

## 4. 第 3 轮：英文/同义改写补强 + 三批留出集

### 4.1 为什么是“修规则 + 换样本”而不是“修到 1.0”

第 2 轮留出集（H01–H08）暴露 2 个漏报后，有两条路：

- A. 直接在 H01/H03 上改正则，跑出 1.0 报出去 → **指标造假**：这批样本已经“看过答案”；
- B. 按缺陷类型改规则 → 换一批**新写**的样本验证 → 如果又暴露新写法，再换一批。

选 B。于是本轮实际跑了两批新样本：`holdout2`（12 份）用来找缺陷，`holdout3`（8 份）用来报数。`holdout2` 一旦被用来定位缺陷，也降级为回归集——这条规则写进了 ADR-011 第 3 轮补充。

### 4.2 规则改动（`app/rules/definitions.yaml`，`version: 3 → 4`）

| rule_id | 改动 | 反向保护（刻意不收的情况） |
|---|---|---|
| `R-DIS-003` | 增英文 `arbitrat…\s+or\s+…court/litigat…` | 不收 “the award may be enforced in any court”（裁决执行的正常条款） |
| `R-DIS-004` | 增英文 `award…may/shall…file/commence/appeal/litigate…court` | 不收 “may be set aside”（撤销裁决的法定救济） |
| `R-INC-001` | 增 `海运费/订舱费用…由卖方承担`、`卖方承担…主运费`、`freight … paid/prepaid/borne by the seller`；窗口 200 → 260 | 不收“出口报关费用由卖方承担”（本就应由卖方承担）；倒装语序排除逗号/句号 |
| `R-INS-001` | 增英文 `insure/insured`、`110% of the invoice value`、`insured value of USD …` | CIF/CIP 完全没写保险仍不触发（Incoterms 默认 110% + ICC(C)） |
| `R-INP-002` | 增英文 `N hours … inspect/notify/claim` | 14 天这类合理期限不触发 |

顺带修掉 holdout2 暴露的两个**真实缺陷**：

1. **子串误命中**：`contains_any: [CIF, CIP]` 会把 “Pa**cif**ic / speci**fic**ation” 当作 CIF → H13 误报。四条术语规则改为“前后非英文字母”边界，同时保留“FOB上海”这种紧跟中文的合法写法；
2. **距离窗口截断**：`R-INC-001` 的 200 字符窗口被 “Freight and Charges” 小标题吃掉（实测 FOB→freight 距离 210）→ H19 漏报。窗口放宽到 260，实测距离写进规则注释。

### 4.3 结果

**holdout2（12 份，H09–H20）——用于找缺陷，已消耗**

```
干净对照：H10 / H13 / H20 零命中（H13 含“出口报关费用由卖方承担，主运费由买方承担”）
```

**holdout3（8 份，H21–H28）——本轮唯一盲测，对外报数只能引用这一组**

```

合同级漏报：H21, H22, H24
```

### 4.4 holdout3 的 3 个漏报（本轮不修）

| 合同 | 真实写法 | 规则为何没命中 |
|---|---|---|
| H21 | “双方可选择提交上海国际仲裁中心仲裁，**亦可**向有管辖权的人民法院起诉” | 中文分支只认“或 / 或者” |
| H22 | FOB 下“卖方**负责支付**自宁波至釜山的主运费及订舱费用” | 倒装分支要求“卖方承担/预付/支付”紧邻 |
| H24 | “examine the goods within **thirty-six (36) hours**” | 只认阿拉伯数字 `\d{1,2} hours` |

三个都是**措辞覆盖**问题（判级逻辑没错），说明“靠正则堆写法”收益递减。下轮修完这三类 + `R-INS-001` 的保额全文级判定后，必须**另写 holdout4** 才能对外报新数字。

### 4.5 指标口径补丁

`coverage` 在留出集上恒为 1.0（gold 每条现象都带 `rule_id`），和 recall 0.571 并排看会很误导。`score_coverage` 现在带 `note` 字段，`run_eval` 在缺口为 0 时打印“覆盖率高不代表识别得出，实际能力看 recall”。覆盖率只在设计集 `gold_rules.json`（52.4%）上才有信息量。

## 5. 界面轮：原生 Web 前端

### 5.1 问题与约束

用户原话是“我需要真正的前端”。当时的界面 `app/ui.py` 是 Streamlit：功能完整，但页面由 Python 生成、每次交互整页重跑。排查时还发现浏览器在 8000 端口请求 `/@vite/client`（Vite 探测，404）、8501 打不开（未启动/端口未监听）。

约束来自 `开发提示词.md`：**禁止前端框架**（React/Vue）、禁止引入 npm 构建链；ADR-009 又要求所有人工决定必须经 `ReviewService.resume()`。所以不能上 Vite，只能手写。

### 5.2 交付物

| 文件 | 内容 |

## 6. 第 4 轮：规则 version 5 + 保额邻近判定 + holdout4 盲测

### 6.1 本轮要解决的两个问题

holdout3 留下两类债：

- **3 个措辞漏报**（H21“亦可”、H22“负责支付”、H24“thirty-six (36) hours”）——判级逻辑没错，纯属写法没进规则；

### 6.2 规则改动（`app/rules/definitions.yaml`，`version: 4 → 5`，仍是 13 条）

| rule_id | 改动 | 反向保护 |
|---|---|---|
| `R-DIS-003` | 中文并列扩表：`或 / 或者 / 亦可 / 也可以 / 仍有权 / 亦有权 / 有权 / 可选择` | 仍要求“仲裁…法院/诉讼”同句出现；H32 仅“申请撤销裁决”不触发 |

### 11.5 后端为什么必须加 `GET /api/rules`

规则页需要“有哪些规则、各自等级与理由”，但直接把 `definitions.yaml` 序列化给浏览器等于泄露判级实现，也容易让前端顺手在本地判级。所以新增白名单投影 `RuleSummary`（`extra="forbid"`），只给 `rule_id / title / category / risk_level / reason / suggestion / requires_extraction`，外加 `ruleset_version`（来自 YAML 的 `version: 5`）与 `red_count / yellow_count`。`risk_level` 是规则定义里的静态等级，**不是**运行时判定；测试断言响应里没有 `condition` / `source`。

### 11.6 字体为什么随包

原先 CSS 里写的是 `fonts.googleapis.com` 的字体链接，违反“禁止 CDN”。下载后发现 Google 对 400/500/600 三个“静态字重”返回的 latin 子集**是同一个可变字体文件**（三份 SHA256 相同）——于是只留一份改名 `ibm-plex-sans-var.woff2`，CSS 里一条 `@font-face` 声明 `font-weight: 100 700`。Windows 的 `mimetypes` 可能不认识 `.woff2`，所以后端启动时显式注册 `font/woff2`，否则浏览器会拿到 `application/octet-stream`。

## 12. 界面轮 3：先判断是不是合同 + 收掉运行环境

### 12.1 起因

用户上传一篇法学论文测试，系统照样切条款、抽要素、判出黄色风险，最后还弹人工确认。根因不是某条规则写错，而是**入口缺少“对象是否正确”的准入判断**——规则是一堆关键词/正则，任何足够长的文本都能命中点什么。同一轮用户还提了两件事：侧栏“运行环境（接口 v0.8.0 / 规则集 v5 / 检查点 sqlite / RAG 关闭）”业务用户看不懂；以及“RAG 为什么是关闭的”。

### 12.2 闸门设计（ADR-012）

新增 `app/services/document_type.py::classify_document(text) -> DocumentCheck`，纯规则、离线、可解释，阈值与词表集中在文件顶部：

| 维度 | 内容 | 分值 |
|---|---|---|
| 身份信号 | 合同抬头（`销售/买卖/采购/供货…合同`、`Sales Contract`）、合同编号（`合同编号：C47`）、买卖双方（卖方/买方、甲方/乙方、Seller/Buyer） | 3 / 2 / 2 |
| 结构信号 | 编号条款（`第X条` / `Article N`）、交易要素（金额/币种/Incoterms/装运）、签署语 | 2 / 1 / 1 |
| 反向信号 | 学术论文（摘要/关键词/参考文献/本文认为/this paper）、法规条文（本法/民法典/总则/Civil Code） | 命中即否决 |

判定：`is_contract = has_identity and not academic and not law and score >= 4`；正文去空白 < 120 字直接判否（并提示扫描件/OCR）。**召回优先**——宁可放过一篇“很像合同”的文档，也不要误杀真实合同。

两处真实踩到的细节（都已写进交接文档第 89/90 条）：

1. 抬头正则初版在全文搜，把正文“货物符合合同约定”当标题 → 只扫开头 12 个非空行、行长 ≤48、排除标点句与 `本合同/符合合同/根据合同`；
2. 合同编号初版在“去空白文本”上匹配且不取值，`合同编号：C47` 取不到 → 改在原文匹配并捕获第二组。

### 12.3 图怎么变

```text
ingest_document → precheck_document ─不是合同→ build_report
                        └─是合同→ segment_clauses → extract_fields → validate_facts
                                  → evaluate_rules → [有 red] → human_review → explain_risks → build_report
```

不是合同：`status=not_contract`、`clauses=[]`、不抽取、不判级、**不触发 HITL**，报告 `findings=[]`、`overall_level=unknown`，摘要写“未执行合同审查”，限制里写明“不含任何风险结论”。`not_contract` 同时进了 `ReviewStatus`、`FINAL_STATUSES`、`STATUS_LABELS`、`ui.py` 映射与前端 `STATUSES`——否则会出现“已停止但还能提交人工决定”。

### 12.4 界面侧

- 删除侧栏“运行环境”整块（接口版本 / 规则集 / 检查点 / RAG 开关），只保留 `/docs` 接口文档入口；`updateRuntime()` 与 `.runtime*` 样式一并移除，并用 `test_runtime_internals_stay_out_of_the_ui` 钉住防止回退。
- 新增“不是合同”页：状态 + 判定置信度 + “判定依据（`reasons`）/ 下一步（`hints`）”两栏 + “重新选择文件”（清空 `localStorage` 与内存会话）。
- 工作台流水线 5 → 6 步，第 2 步“判断类型 / 不是合同直接停止”；顶部提示改成“论文、法规、说明书会被直接拒绝，不进入判级”。
- `.app` 改为 `grid-template-rows: auto minmax(min-content, 1fr)`，内容少时 sheet 不再浮在中间。

### 12.5 RAG 为什么默认关闭（回答用户）

不是故障，是 ADR-007/008 的产品默认值：RAG 只给**解释**补知识片段，**不参与判级**；知识库未就绪时默认关闭，避免“检索不到”被读成“没有风险”。开启方式：`.env` 里 `RAG_ENABLED=true`（`00_PROJECT_STATE.md` 记录的 `AGENT_ALEX_RAG_ENABLED=true` 为等价前缀形式）；查看当前值：`GET /health` 的 `rag_enabled`。本轮按要求把它从业务界面移除——排查去 `/docs`，不占用户视野。
