## 1. 本轮输入

用户指令（原文）：“我新增了60份模拟合同，请你查收，在knowledge中，然后继续下一步”。

查收结果与用户描述有差异，先记录事实：

| 项 | 实测 |
|---|---|
| 新增文件 | `data/knowledge/模拟合同1.md … 模拟合同6.md`（6 个） |
| 合同份数 | **50 份（C01–C50）**，不是 60 份 |
| 缺失编号 | 未发现 C51–C60；逐个 `## Cxx` 标题核对无遗漏 |
| 每份附带 | 「条款—问题映射摘要」表格（条款 → Q 编号 → 期望召回 → 干扰项） |
| 结构 | `## Cxx · 场景` → `**SALES CONTRACT**` → `### 第X条 …` → `### 签署页` → 摘要 |
| 特点 | 大量占位符 `[C] 天`、`[X]`、`[A]`；专业度高（CISG 排除/未排除、CIF 保险、或裁或审等） |

**处理决定**：模拟合同是**评测输入**，不是法规知识，因此

1. 原始 `模拟合同N.md` 保持不动（用户原始文件，不裁剪、不改写）；
2. **不写入** `data/knowledge/manifest.yaml`（不影响 RAG 引用白名单）；
3. 用脚本拆成单份合同 `data/contracts/C01.md … C50.md`（生成物，可重建）；
4. 摘要解析为结构化 gold，放 `data/eval/gold_contracts.json`。

## 2. 做了什么

### 2.1 `eval/prepare_contracts.py`（新建）

- 正则定位 `## Cxx · 场景` 与 `> **条款—问题映射摘要（Cxx）**`，按合同边界切片；
- 单份合同正文保留 `**SALES CONTRACT**` 与 `### 第X条`，剥离场景标题与摘要（避免评测时把答案喂给系统）；
- 解析摘要表格为 `expectations[]`：`clause / questions / expected_recall / distractors`；
- 输出 `data/eval/gold_contracts.json`：`version / note / contract_count / contracts[]`，其中 `note` 明确“这是检索期望，不是规则判级 gold”；
- 运行结果：**50 份合同、105 条映射、全部解析成功**。

### 2.2 `eval/run_eval.py`（新建）

- 用 `ReviewService.in_memory()` 逐份跑完整规则链路（解析 → 切分 → 规则），**不调用 LLM、不需要 Key**；
- 只统计“未跳过且等级为 red/yellow”的规则，输出：
  `rule_engine_version / rule_count / contract_count / contracts_with_hits / contracts_without_hits / level_counts / hit_counts / contracts[]`；
- 结果写 `eval/results/rules-YYYYMMDD.json`，并在文件内写明“未命中不等于无风险”；
- 由于规则级 gold（`合同 × rule_id → red/yellow/pass`）尚未标注，**不计算 precision/recall**。

### 2.3 首轮基线暴露的两个真实问题

| 问题 | 证据 | 处理 |
|---|---|---|
| `R-TRD-001` 在 40/50 份合同上误报“未约定 Incoterms 版本” | 50 份合同全部写 `Incoterms® 2020`，原正则 `Incoterms\s*(19|20)\d{2}` 不匹配 `®` | 正则改为 `Incoterms\s*[®™]?\s*(?:19|20)\d{2}`，规则 version 1.0 → 1.1 |
| 规则覆盖严重不足 | 修正后 45/50 全 pass，仅 5 份命中 `R-PAY-002` | 扩充 6 条规则（见 2.4） |

> 顺带核实：`R-PAY-002` 的 5 次命中（C39–C43 一类）不是误报——那些合同确实没有付款条款（已逐份查看 C39 全文确认）。

### 2.4 规则集 7 → 13 条（`app/rules/definitions.yaml`，`version: 3`）

| rule_id | 主题 | 等级 | 正则/条件要点 | 命中 |
|---|---|---|---|---|
| R-DIS-003 | 仲裁与诉讼并列（“或裁或审”） | red | `仲裁[^。]{0,60}(?:或|或者)[^。]{0,40}(?:人民法院|法院|诉讼)` | C47 |
| R-DIS-004 | 仲裁裁决后仍可向法院起诉 | red | `仲裁裁决[^。]{0,30}后[^。]{0,60}(?:人民法院|法院|诉讼)` | C48 |
| R-INS-001 | CIF/CIP 约定投保但未写保额/比例 | yellow | CIF/CIP + 保险表述 + 无“保额 … %/合同价” | C04 |
| R-INC-001 | 贸易术语与运费承担矛盾 | yellow | `(?:FOB|EXW|FCA)[\s\S]{0,160}运费由卖方(?:预付|承担)` | C11 |
| R-INC-002 | FOB/EXW 用于整箱集装箱货物 | yellow | `(?:FOB|EXW)[\s\S]{0,120}(?:集装箱|FCL|拼箱|LCL|堆场)` | C23 |
| R-INP-002 | 检验/通知期限以小时计（极短） | yellow | `\d{1,2}\s*(?:小时|hours?)[^。]{0,30}(?:检验|通知|异议)` | C09 |

三个“踩过的坑”，已写进 ADR-010 与交接文档：

1. **`®` 必须容忍**：ICC 官方写法是 `Incoterms® 2020`；
2. **跨句要显式允许**：C11 的 FOB 与“运费由卖方预付”之间隔着句号，必须用 `[\s\S]{0,160}` 而不是 `[^。]`；
3. **不要重复 Incoterms 默认规则**：`R-INS-001` 只在“约定了投保但没写保额”时触发；CIF 完全没写保险条款（C09/C15/C40、干净样例）不触发，因为 Incoterms® 2020 已默认 110% + ICC(C)。

### 2.6 评测结果（`eval/results/rules-20261027.json`）

```
rule_count      : 13
contract_count  : 50
contracts_with_hits : 11
level_counts    : {"pass": 39, "yellow": 9, "red": 2}
hit_counts      : {"R-PAY-002": 5, "R-DIS-003": 1, "R-DIS-004": 1,
                   "R-INS-001": 1, "R-INC-001": 1, "R-INC-002": 1, "R-INP-002": 1}
```

**怎么读这组数字**：

- 只能说明“规则在哪份合同上触发”，**不是准确率**；“39 份未命中”不等于这 39 份无风险，而是**规则没覆盖**（不可抗力缺失、责任上限、质保期、所有权保留、合规等主题尚未做）；
- 每条新规则只命中 1 份，且在两份样例上零命中，说明本轮规则是“窄而准”，不是“广而糙”；
- 6 条新规则是在**同一批 50 份合同**上设计与验证的，属于同分布验证，不能据此宣称泛化精度（ISSUE-020）。
